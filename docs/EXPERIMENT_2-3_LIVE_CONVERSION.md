### 表示と確定の食い違い (査読 推奨 5。コードの読みで事実。実機は未確認・要実機確認)

  - 4 文字のしきい値 (`LiveConvert` の `:2322` を通らない) → 3 文字以下の区間も、表示はかななのに確定では漢字になる。
  - 左文脈 (`PrecedingForConversion`)、Core のユーザー辞書の分割 (`:1740`)、手がかり辞書 (`ContextRules`)、Core の学習 (`History`)、助詞をかなのままにする規則 (`:1964`) などの `ConvertJapanese`/`ConvertWithEngineOnce` の後処理。azooKey 側の学習 (`Converter.swift:96`、`learningType: .inputAndOutput`) は azooKey の中なので効く。
  - 結果として、ライブ表示では登録語・学習した語・助詞のかなが出ていても、Space の確定では別の文字になりうる。
- Enter と、全体が英数字のときの Space (`:1003-1006` → `Commit` → `CurrentDisplay`) は表示どおり。違うのはこの 1 経路だけ。

### Zenzai ON のときの扱い
- **ライブ変換専用の分岐は無い。** ライブ変換も Space の変換も同じ `MeltypeConverter` を通り、Zenzai が ON でモデルが使える (`zenzaiActive`) なら、**すべての変換要求**に `zenzaiMode` (上限 3) が付く (`Converter.swift:147-168`)。**左文脈が付くのは変換の要求だけ**で、予測は `context: nil` で要求する (`Converter.swift:345-347`)。上の Space の `Convert` の経路も左文脈なし。つまり Zenzai を ON にすると、ライブ変換の表示も Zenzai の結果になる (コードの読み。実機の記録は無い)。
- 1 キーで続けて出る要求 (予測 → ライブ変換 → 文節候補) の合計が 300 ms を超えることが 3 キー続くと、そのプロセスでは Zenzai をやめる。遅くないキーが 1 つ入れば数え直す。モデルを読み込めなかったときもやめる (`Converter.swift:69-73, 200-231`、`mac/README.md:74`)。その間もライブ変換は ON のままで、Zenzai なしの結果になる。
- Zenzai は**既定 OFF** (設定 + モデル 74 MB を初回取得。`MacSettingsCatalog.cs:95-96`)。既定のままの利用者のライブ変換は、従来の azooKey 辞書変換のまま。
- (査読 任意 6、記録のみ・未確認) Core の `_liveCache`・`_conversionCache` の鍵に Zenzai の状態が入っておらず、捨てるのは学習のときだけ (`CompositionController.cs:269-276`)。Zenzai を ON にした直後や安全弁で止まった直後は、同じ読み・同じ文脈で前の結果が出続けることがある。実機で Zenzai の差を見るときは新しい入力欄で試す。

## 2. Zenzai の計測結果から、ライブ変換の精度向上にどこまで使えるか

引用は `ZENZAI_EXPERIMENT_2026-10.md` のみ (M4 Max、CPU 版、212 文、第一候補の一致で採点)。

使える根拠:
- 第一候補の一致: なし 69.3% → 上限 3・左文脈なし 86.3% (**+17.0 pt**) → 左文脈あり 91.0% (**+21.7 pt**)。悪化は 7 件 (3%) / 3 件 (1.4%) (`:9`)。文書は「左文脈なしの +17 pt を主に見る」としている (正解表の 142 文は LLM が作った教科書的な文で zenz に有利な可能性があり、左文脈の 30 文は「1 文で答えが決まるように作ってあり、実際の入力欄の直前の文字とは性質が違う」ため。`:20`)。妥当な別表記を甘く採点しても約 +20 pt (`:21`)。
- 速さ: 1 キー (予測 + 文脈あり変換 + 文脈なし変換の合計、最悪ケース) が、なし p50 2.9 / p95 7.3 ms、上限 3 で p50 30.8 / p95 61.0 ms (最大 120 ms)。読み 21 文字以上の p95 は 78 ms (K68)。目安は p95 80 ms 以下 (`:10`)。ライブ変換は 1 キーごとに走るので、この「1 キー合計」がそのまま関係する数字。
- メモリ: アクティビティモニタ +30 MB、物理メモリ約 +70〜100 MB (`:11`)。
- 製品の配線 (左文脈・キャッシュ鍵・安全弁) は実装済み (`Converter.swift`)。

文書に無い・未確認 (推測で埋めない):
- **ライブ変換の表示だけの精度**は未計測。実験は読み全体を変換した第一候補の一致で、「4 文字以上のライブ表示が正しい漢字か」を測っていない。4〜6 文字の短い読みでの伸びは、文書に内訳が無く未確認。
- **日英混在の入力**は実験に無い (azooKey に渡るのはかなだけ。文書にも「日英混在の文は無い」)。
- **ライブ表示と、Space で確定した文字が食い違うか** (§1 の「表示と確定の食い違い」)。コードの読みでは食い違いうるが、実機では未確認。
- M1・8 GB 級の速さ、メモリが逼迫した直後の速さは**未計測** (K67、`:22`)。
- 打鍵中に表示が揺れる (ちらつく) かの体感は文書に無い。GPU 版は llama.cpp b4846 で落ちるため CPU 版のみ。
- 4 文字のしきい値を Zenzai で下げられるかは未計測 (しきい値の根拠は辞書変換の短い断片の的外れ。ニューラルで変わる保証は文書に無い)。

結論: **Zenzai による精度向上には、新しい実装は要らない。Zenzai を ON にすれば、ライブ変換は既に Zenzai の結果になる (コードの読み)。** 2-3 の「精度向上」の実体は (a) Zenzai を既定 ON にするか、利用者に ON を勧めるか、(b) ライブ変換に絞った計測を足すかの判断 (§4 (B) で決める)。
ただし、§1 の「表示と確定の食い違い」が実機で確かめられたら、それは 2-3 の中で数少ない**実装する価値のある候補**になる (本家と共通のコードなので、上流と比べる表でも扱う)。実機で確かめるまでは実装しない。

- 得: ライブ変換があることと、その動き (英単語は英字のまま、日本語の区間だけ漢字) が「できること」で見つかる。変更は README の 2 行 (1 行追加・1 行修正) で、コードに触れない。裏は K28 と `RenderSegments` で取れている。取り消しも容易。

- ライブ変換は本家と共通の機能。この前面化を X の投稿や `COMPARISON_UPSTREAM.md` に広げるときも、Mac 版独自の機能として書かない。
- 適用はリョウ判断 (公開物 = README の変更になるため、勝手に push・公開しない)。

### (B) Zenzai を既定 ON にする — **no-go (今は何も作らない、ON も勧めない)**
- 得: Zenzai の計測は +17〜22 pt と大きく、ライブ変換も自動で恩恵を受ける (コードの読み)。追加の実装は不要で、既にコードに入っている。
- 損:
  - **プライバシーの約束と矛盾する (最も強い理由)。** README は「通信するのは新しい版の確認と、Zenzai を ON にしたときのモデルの取得だけ」(54a2002 の 25 行・188 行) と、「ON にしたときだけ (既定は OFF)、変換モデル (約 74 MB) を…取得」(196 行) を約束している。既定 ON にすると、利用者が同意する前にモデル (73.9 MB) を取りに行くことになる。
  - M1 級の速さが**未計測**で、ライブ変換は全キーで走るため遅さが直接体感に出る (安全弁はあるが、働くのは 300 ms が 3 キー続いてから)。
  - ライブ変換だけの精度・日英混在は未計測で、効果を断言できない。
- 利用者に ON を勧めるか: **勧めない (README は中立のまま)。** 差分の Zenzai の行は「既定 OFF」を足すだけで、「ライブ変換の表示にも使われます」は書かない。勧めるときは、K67 (M1 級は未計測) と K68 (読みが 20 文字を超えると遅くなる) を一緒に書く。
- やり直す条件 (すべて満たしたら、既定 ON を go/no-go にかけ直す):
  1. 速さ: M1 級 (または 8 GB 機) で 1 キー p95 を測り、**80 ms 以下** (実験と同じ目安、`:10`)。
  2. 精度: ライブ表示の単位 (`LiveConvert` の出力。4 文字のしきい値を含む) で小さな評価を足す。対象は **4〜8 文字の読み**と**日英混在の入力**。合格の基準は実験と同じ **+5 ポイント以上、悪化 1 割以下** (`:9`) を、それぞれの集合に当てはめる。
  3. プライバシー: 1・2 を満たしても、既定 ON はプライバシー節の約束 (25・188・196 行) を変えるか、初回に同意を取る流れ (例: 初めて使うときに「モデルを取得しますか」と聞く) を作るかが先。どちらもリョウ判断。

### (C) しきい値 (4 文字) の引き下げ — **no-go**
- 得: 短い語も Space なしで漢字になる。
- 損: 3 文字以下は的外れな漢字になりうる (コードのコメントの例: きょ → 居、きょう → 喬)。3 文字の語がよくなる場合 (かんじ → 漢字 など) もあり、どちらが多いかは未計測。Zenzai で改善するかも未計測。**しきい値は本家と共通の Core の定数なので、変えると本家と挙動が分かれ、上流の変更を取り込みにくくなる。**

### 総合
2-3 は **「A は実機確認 1 のあとで go、B は no-go (プライバシーの約束と計測待ち)、C は no-go」で進める。** 2-3 の中身はほぼ README の文章修正になる。Zenzai による精度向上の本体は Phase 1-1 の成果に乗っており、新しい変換コードは要らない。唯一の実装候補は §1 の「表示と確定の食い違い」で、実機で確かめてから、本家と共通のコードとして扱いを決める。
