## 結論 (先に)

- 提案: **no-go** (理由は末尾の「go / no-go 提案」)。Core の実験用フラグは **main に入れない** (「main への入れ方」)。
- **主な理由: 「英語の名詞句で始まる日本語の文」の直後の日本語を壊す。** `Pull Request を` + `made` → 現行 `まで` / 案 `made`、`Google Drive に` + `age` → `あげ` / `age` のように、この型 12 件のうち **6 件を英字のまま残す** (比率 0.5・0.7・0.8。0.9 でも 5 件)。この型の前 20 文字は 9 割前後 (0.89〜0.94) が英字なので、閾値を上げても防げない。12 件は査読者が足した例で、期待は査読者の判断 (実機の記録ではない)。
- 私が書いた 68 件では **純増減 0** (比率 0.5 で 得 6 / 損 6、0.7 で 得 5 / 損 5)。ただしこれは作例の配分 (分岐 20 件の中で、続きが日本語の語か英語の語か) で決まる数で、案の実力ではない。68 件には上の型が 1 件も無い。査読で足した 56 件では 0.5 で 得 5 / 損 9、0.7 で 得 3 / 損 6 と **負け越した**。
- 閾値 0.8・0.9、片側 (日本語側だけ・英語側だけ) の案も測った。どれも負け越すか、得が消えるか、引き分け (0.5 日本語側だけ 得 8 / 損 8) か、勝ち越しが 1 件で作例の配分の範囲に収まる (結果 3)。**比率の閾値の調整では直らない。**
- 結果が変わるのは、「最後の 1 文字の向き」と「前 20 文字の多数派の向き」が逆の文脈だけ。案が狙った pull request no 型 (日本語の文の中の英単語の直後の `no`) は、現行でも案でも英語のまま (期待は の) で、案では直らない。
- 案が効くのは、入力を始める時点で入力欄の文字を読む場合だけ。Meltype で続けて打っている途中 (自分の確定から 1.5 秒以内) は、前の文字を読まずに自分の確定の向きを使うので、案は働かない (「何を比べたか」)。得も損も、実際の利用では下の表の見た目より小さい。

### 日本語文中の英単語が英語側へ寄る副作用 (pull request no)

- 現行で既に `今日は pull request ` の直後は英語寄りで、`no` が英語のまま残る (期待 の)。末尾 1 文字が `t` で英語と数えられるため。
- 案は、この型では前 20 文字の多数派も英語 (`今日は pull request ` は英 11・日 3、比率 0.79) なので **同じ英語**。出力は現行と同一で、**副作用が増えも減りもしない** (15 件の JA尾EN 全件で、どの方式も現行と同一)。
- 直すには別の仕組み (CompositionController.cs L644 のコメントにある PrecedingEnglishSentence を使わない理由の見直しなど) が要る。
- 英語の文の末尾に日本語が 1 語あると日本語寄りになるのは現行の弱点で、両側の案は英語に寄せて一部 (`fix the bug` `devote` `morally`) を直すが、`to` `so` `go` のような短い曖昧語は、前文脈が英語になっても `と` `そ` `ご` のまま直らなかった (BeforeScore の +1 では足りない)。

## go / no-go 提案: **no-go (「前 20 文字の比率」案は採らない)**

- 根拠:
  1. **英語の名詞句で始まる日本語の文 (R3 型) の直後の日本語を、12 件中 6 件壊す** (0.5・0.7・0.8。0.9 でも 5 件)。現行はこの 12 件をすべて正しく出している。
  2. 純増減は、私の 68 件では 0 だが、これは作例の配分で決まる数。R3 型を含む査読の 56 件では 0.5 で 得 5 / 損 9、0.7 で 得 3 / 損 6 と負け越した。
  3. 閾値 0.8・0.9・片側だけも測り、どれも負け越すか、得が消えるか、引き分け (0.5 日本語側だけ 8/8) か、勝ち越しが 1 件の誤差の範囲だった。比率の調整では直らない。
  4. 狙いの pull request no 型は直らない。
- 根拠にしないもの: 「英語が仮名まじりに壊れる」重い壊れ方は、現行も鏡の文脈で起こしている (案は文脈を入れ替えるだけ)。掃引の 2.1% は掃引の作りで決まる数。
- 得もある: 日本語の長い文の末尾が英単語のとき、次の日本語の曖昧語 (sushi・sake・kanji) が仮名になる。英文の末尾に日本語が 1 語あるとき、次の英語の語が壊れなくなる。記号の全角/半角が文脈に合う。これを狙うなら、比率ではない別の仕組みが要る。**未測定のまま残す案**: 直近の語数 (最後の何語が英語か) を使う案、記号の全角/半角だけに比率を使う案。
- 2-2 の主な成果は、実験 A の「ホスト別の取得率の表」(HOST_COMPAT.md に足す) になる可能性が高い (推測)。

## main への入れ方

- no-go なので、**Core の実験用フラグ (`ExperimentalContextRatio`・`ExperimentalContextSide`・`ContextRatio`・`LanguageOfContext`) と、それを使う `ContextExperiment.cs`・`Program.cs` の `--ctx-experiment` は main に入れない。** main の `BeginComposition` と `ExplainDetection` は `LanguageOf(before)` のまま。

  - 損: 再測定するときは、実験ブランチを取り出す必要がある。
- main に入れるのは文書 2 本 (この文書と [EXPERIMENT_2-2_HOST_CONTEXT.md](EXPERIMENT_2-2_HOST_CONTEXT.md)) と、表 2 つ (`eval/context/context-cases.tsv`・`eval/context/review-cases.tsv`) だけ。表は前文脈つきの判定の例として、別の案を測るときに使える。

  - **2 つのブランチは手元にだけあり、GitHub (origin) には無い** (2026-10-15 に `git ls-remote --heads origin` で確認)。文書を main に入れて push すると、公開の main の文書から再現のコードを辿れない。ブランチを公開する (push する) かは公開行為なので **リョウさんの判断事項** で、この作業では公開していない。公開しない場合、再現には手元のリポジトリのブランチが要る。
