## 1. Q41 ライブ変換の表示のまま確定すると学習されない

### 今の動き (使い捨てのテストで再現)

確定の処理は `CompositionController.cs` の 2998 行 `if (converting && !_reconvertRomaji) Learn();` です。

- ライブ変換の表示は「変換中」(`converting`) ではありません。そのため、表示のまま Enter で確定すると `Learn()` が呼ばれません。
- 呼ばれないのは、`Learn()` のうちの漢字の学習の部分です。英字 / かなの学習 (`LearnLanguage`) は else 側で今も走ります。

| ID | 手順 | 結果 |
| --- | --- | --- |
| R1a | ライブ変換 ON。たんいを → 単位を を 1 回学習済み。`tanniwotoru` → Enter | 表示・確定とも「単位を取る」。変換エンジンへの学習 0 回、予測用の回数は 1 のまま、登録提案の回数 0 |
| R1b | 同じ読みを Space → Enter | 変換エンジンへの学習 1 回、回数 1 → 2、登録提案の回数 1 (対照。全部動く) |
| R1c | こうえん → 講演 を学習済み (エンジンの 1 番目は公園)。3 回確定する | ライブ表示 → Enter では表示は毎回「講演」で、学習 0・回数そのまま・登録提案の回数 0。Space → Enter では学習 3 回・回数 4・登録提案の回数 3 で、提案が 1 件出る |
| R1d | ライブ変換 OFF でかなのまま Enter / ライブ変換 ON で Shift+Enter / 暗黙の確定 (フォーカス移動など) | どれも学習 0 (暗黙の確定は、もともと学習しない仕様: 2956〜2959 行、3006 行のコメント) |
| R1e | ライブ変換 ON で `kouengithub` + Space (英語で終わる) | 表示は「講演github」なのに、確定は「公園github 」。学習 0 |

R1e の「表示と確定の食い違い」は、[EXPERIMENT_2-3_LIVE_CONVERSION.md](EXPERIMENT_2-3_LIVE_CONVERSION.md) の「確定時」の行に書かれている既知の動きです。この経路は学習と選び直しの記録を使わない `Convert` を通ります (1211 行)。

### もしライブ表示の Enter でも学習したら起きうること

- 見ずに確定した誤変換を azooKey が覚えます。
  - azooKey への学習は、選び直していない文節もすべて渡します (3897〜3905 行)。
  - Space → Enter でも今すでに同じことが起きているので、違いは「候補をよく見たかどうか」の程度です (推測)。
  - azooKey の学習は 1 回で効きます (Q42 の計測: Zenzai OFF で、学習なしで正解だった 14 行のうち 12 行が、学習した同音語に変わった)。誤りを覚えると直りにくくなります。
- 暗黙の確定 (K95・Q16 の、入力の途中で切られた確定) まで含めると、途中の表示を学習します。暗黙の確定は外す必要があります。
- 英語で終わる Space の経路 (R1e) は表示と確定がずれるので、ここに学習を付けると見ていない文字列を覚えます。
- Q17 のような乗っ取りは、選び直しの記録 (`Remember`) が選び直した文節だけを対象にしているので、今の `Learn()` を呼ぶ形なら起きません。
- 学習のたびに変換結果の覚えを捨て、azooKey の学習データを書きます。確定のたびの書き込みが増えます (未計測)。

## 2. Q42 一度選び直した語が、文脈で選んだ結果に勝つ

### 今の動き (使い捨てのテストで再現)

各文節の最初の候補は、次の順で最初に当たったものになります (`ConvertWithEngineOnce`、2349 行)。

計算の記号 → 文脈の手がかり辞書 (`contexts.txt`) → **選び直しの記録** (`ConversionHistory`) → 小さな補正 → 変換エンジンの結果

選び直しの記録は「文節の読み → 選んだ文字列」だけで、文脈を持ちません (`ConversionPreferences.cs` の `ConversionHistory`)。

| ID | 手順 | 結果 |
| --- | --- | --- |
| R2a | 偽のエンジンは、文脈に「大学」があれば こうえん → 講演、無ければ公園を返す。文脈「大学の」で講演と出たのを公園に選び直して確定する。その後、文脈「大学の先生の」で変換する | 学習なしの対照は講演。学習後は Space でもライブ表示でも公園が先頭 (エンジンの講演が負ける) |
| R2b | あつい → 厚い を学習済み。エンジンは常に「熱い」 | 「今日の気温は」の後は暑い、「お茶が」の後は熱い (手がかり辞書が勝つ)。「大学の」の後は厚い (手がかり辞書が当たらなければ記録が勝つ) |

### azooKey 自身の学習も、Zenzai の文脈の判断を上書きする (実エンジンでの計測)

正解表 `eval/kanji/kanji-cases.tsv` の、前の文 (`left_context`) で答えが決まる 32 行 (16 対) を使いました。各対で片方の語を azooKey に学習させてから、もう片方の文を前の文つきで変換します。

- 学習の置き場は計測ごとに新しく作っています
- Core の後処理は通していません (azooKey だけの値)
- 同じ計測を 2 回行い、結果のファイルは一致しました

| Zenzai | 学習の形 | 対象の行の正解数 (32 行) | 学習なしで正解だった行のうち、学習した語に変わった数 |
| --- | --- | --- | --- |
| ON | 学習なし | 24 | – |
| ON | 単語の形 (読み → 語を 1 回。3 回でも同じ) | 18 | 5/24 (ほかに 1 行は別の語に崩れた: 公園を学習 → 講演の行が公演に) |
| ON | 文の形 (文全体を確定した形。1 回でも 3 回でも同じ) | 10 | 13/24 |
| OFF | 学習なし | 14 | – |
| OFF | 単語の形 | 2 | 12/14 |
| OFF | 文の形 | 1 | 13/14 |

- Zenzai OFF では、もともと azooKey に文脈が渡らないので、学習した語が先頭に来るのは期待どおりの動きです。
- 問題は Zenzai ON のときです。Core の選び直しの記録は文脈を見ずに必ず勝ち (R2a)、azooKey の学習も半分前後の行で文脈の判断を上書きします。

## 3. Q43 製品では前の文が Zenzai に渡らない

### 今の動き (使い捨てのテストで再現)

変換エンジンに渡す文脈は `ContextOf` (`CompositionController.cs` 2499〜2507 行) で作ります。

- キャレットの前の確定済みの文字の最後の文字が日本語のときだけ渡します。
- 最後の「。」「！」「？」改行より後ろを取り、その末尾の最大 10 文字にします。
- Swift が入力欄から読むのは、キャレットの前の 20 文字だけです (`InputController.swift`)。

| キャレットの前の文字 | 変換エンジンに渡る文脈 |
| --- | --- |
| 大学の先生の話を聞いた。 | なし |
| 今日は大学の | 今日は大学の |
| 昨日は大学の先生の研究室で | 大学の先生の研究室で (末尾 10 文字) |
| 今日はGitHubのレポジトリで | Hubのレポジトリで (英単語の途中で切れる) |
| 大学の先生の話を聞いた。来週の | 来週の |
| 大学の先生の話を聞いた、 | の先生の話を聞いた、 |

この切り方は Mozc / Microsoft IME に合わせた本家の形で、Zenzai の導入のときに見直した記録はありません。

- [ZENZAI_DESIGN_1-1.md](ZENZAI_DESIGN_1-1.md) は、長さを「azooKey に任せる」としか書いていません。
- Zenzai の実験と自己テストは、正解表の前の文を Core を通さずに Swift へ直接渡していました。

## 4. Q44 「語幹の候補 + 助詞」を選ぶと azooKey が学習しない

- Swift の学習 (`Converter.swift` の `learn`) は、文節の読みで変換した候補の中から、確定した文字列と同じ候補を探して azooKey に渡します。見つからない文節は黙って飛ばします (300 行)。
- `candidates(for:)` が Q27 で足す「語幹の候補 + 助詞」(読み `かいぎで` なら、語幹 `かいぎ` の候補に「で」を付けたもの) は、語幹の読みで変換した候補に助詞を付けた文字列です。文節の読みの候補には入っていないので、選んで確定しても学習されません。
- Q42 の計測で、文全体を学習させたときに鍵の文節が学習されない対 (講演は・意志が・石が・洗濯を・開放された) として見つかりました。
- コードと計測で確かめましたが、実機では確かめていません。選び直しの記録 (Core の `ConversionHistory`) の側は覚えるので、次からの先頭には出ます。学習されないのは azooKey の側だけです (推測)。
