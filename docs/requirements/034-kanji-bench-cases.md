# 034 かな漢字の正解表に比較ベンチの 180 文を取り込み、Zenzai OFF/ON を変更ごとに測れるようにする

## 背景 (誰が、何に困っているか)
- 外部の比較ベンチ (xlsx) の A (日英混在 60 文) と B (かな漢字 120 文) は、Mac の漢字変換の精度を測る材料になる。しかし xlsx の fork の数字は Linux + Mozc のもので Mac には当てはまらない。Mac の経路 (azooKey、任意で Zenzai) で測り直した結果は手元の一時フォルダーにあるだけで、**変更するたびに測り直す手順がリポジトリに無い**。
- 既存の正解表 `eval/kanji/kanji-cases.tsv` (212 文) は 142 文を LLM が作っており、AJIMEE-Bench (第三者作、200 件) は実行時に取る CC-BY-SA のデータでリポジトリには入れられない。GPL-3.0 の出典なら入れてよい (このリポジトリも GPL-3.0-or-later)。

## 今の動き (既に分かっていること)
- 測る口: `MeltypeIME --convert-eval <tsv> [--weights <gguf>]` (4 列 id / 読み / 正解 (`|` 区切り) / 左文脈。製品と同じ `MeltypeConverter.clauses` の第一候補)。採点と差の出し方は `tools/ajimee-eval.py` (AJIMEE 専用。表は実行時に取る) にあり、**任意の 4 列の表を、OFF と ON で流して前回と比べる道具は無かった**。
- 出典と照合した結果 (2026-11-25、機械で確かめた):
  - A: 本家 `yksr-melt/Meltype` の `tools/mozc-compare-cases.tsv` (main 01672c87、最終変更 a2bf6e00)。本家の clone の `origin/main` の内容と、GitHub の raw (コミット固定) の内容の md5 が一致。60 行が xlsx の A と **順序・文字まで同一** (`cases.json` と突き合わせた)。ライセンス: GitHub の API で GPL-3.0。
  - B: `Serugu/Meltype-Zenzai-Vulkan` (本家のフォーク) の `tools/zenzai-cases.txt` 80 文 + `tools/zenzai-holdout.txt` 40 文 (どちらも最終変更 6973b307、先頭は 520ac08)。raw (コミット固定) と取得したファイルの md5 が一致。xlsx の B 120 文の期待が原文と **順序・文字まで同一**。リポジトリのライセンスは GPL-3.0 (API・LICENSE 本文で確認)。
  - 読み: B は原文にかな (「文 / 読み」) があるのでそのまま使った。A は原文がローマ字の打鍵だけなので、親が作った日本語の部分の読み (73 部分) を、**別に書いた独立のローマ字→かな変換器**で作り直して突き合わせた (73 部分すべて一致)。B の打鍵を同じ変換器でかなにしたものも、原文の読みと 120 文すべて一致した。
- 原作者の `docs/ZENZAI.md` (6973b307): `zenzai-cases` は「同音異義語の多い 80 文。**重みの調整に使った**」、`zenzai-holdout` は「調整に使っていない 40 文」。つまり B は **Zenzai を評価する・調整するための、同音異義語に偏った表**。

## minimum の要件 (これだけは満たす)
1. 出典・ライセンス・コミット・変えたことを表の頭に書いた 2 つの表を `eval/kanji/` に入れる。
   - `bench-mixed.tsv` (A。60 文を英単語の所で切った日本語の部分 73 行。左文脈 = その前の期待 (英単語を含む)。id `M01_0` …。文の単位は `M01`)
   - `bench-homophones.tsv` (B。120 文。id `Z001`〜`Z080`・`H001`〜`H040`)
2. 期待に無理がある行は `|` 区切りで許容を **足す**。原文の期待は 1 つ目に残す (厳密一致 = 1 つ目と同じ)。正解を減らす変更はしない。足した行と理由は下の表に全部書く。
3. `tools/kanji-bench.py`: 表を `--convert-eval` で OFF (必ず) と ON (`--weights` のとき) で流し、表ごと・OFF/ON ごとに行・文の件数 (厳密一致・許容あり) と p50/p95、前回の記録 (`--save` の JSON) との差 (当たり → 外れ・外れ → 当たりの行) を出す。`--fail-on-regression` で当たり → 外れがあれば終了コード 1。
4. 基準値を測って記録 (`eval/kanji/bench-baseline.json`) と下の表に残す。
5. B が同音異義語に偏ることと、過学習を避ける確かめ方を、表の頭と文書に書く。

## 非目標 (今回はやらない)
- Core・Swift のコードの変更 (判定は変えない。boundary-sweep は不要)。変換の精度を上げる変更そのもの。
- 英単語の部分 (google・github など) を測ること。A の表は**日本語の部分だけ**で、英語と日本語の判定は `eval/cases` の仕事。そのため A の「memoを取る」の メモ/memo、「このappは便利です」の アップ/app は、この表では表せず (英単語の部分は測らない)、何も変えていない。xlsx の A の数字 (英単語を含めた文の一致) とは別の数字になる。
- 速さの M1 級での測定 (下の基準値は M4 Max だけ)。
- 辞書・規則をこの表に合わせて足すこと (下の過学習の注意)。

## 使い方 (変更ごとの測り方)
```bash
swift build -c release --package-path mac
W="$HOME/Library/Application Support/Meltype/models/zenz-v3.1-small-Q5_K_M.gguf"   # ON を測るとき (読むだけ。通信しない)

# 変更の前: 記録を取る (木のすぐ外に置く。表が変わらない限り、同じビルドなら第一候補は毎回同じ)
python3 tools/kanji-bench.py --binary mac/.build/release/MeltypeIME --weights "$W" --save /tmp/bench-before.json
# 変更の後: 前の記録と比べる (当たり → 外れが 1 行でもあれば終了コード 1)
python3 tools/kanji-bench.py --binary mac/.build/release/MeltypeIME --weights "$W" --baseline /tmp/bench-before.json --fail-on-regression
```
- 基準 (main 9ded846) の記録はコミット済みの `eval/kanji/bench-baseline.json`。`--baseline eval/kanji/bench-baseline.json` で main に対する差が出る。大きな変更を取り込んだら、同じ手順で `--save` して入れ替える (差の根拠を文書に書く)。
- 突き合わせは「記録した第一候補」を**今の表**で採点し直す。表に許容を足したことは、エンジンの変化に数えない。
- `--weights` を付けなければ OFF だけ測る (製品の既定。2 表で約 2 秒)。ON は約 8 秒 (M4 Max で、ビルド済みのバイナリを使うとき。どちらもビルドの時間は含まない)。
- 自己テスト: `python3 tools/test_kanji_bench.py` (Swift・モデル不要。CI で回る)。表の件数・出典・左文脈・足した行が文書に載っていること・記録が全行を持つことも見張る。

## 過学習の注意 (B の使い方) — 必読
- B (`bench-homophones.tsv`) は Zenzai の評価・調整用に作られた表で、**同音異義語 (意思/石/医師、機械/機会、暑い/熱い/厚い、橋/箸/端 など) に偏っている**。一般の文の精度の代表ではない。Z (80 文) は原作者が重みの調整に使った側で、H (40 文) も同じ偏りを持つ。
- **この表に合わせて辞書・規則・学習の初期値を足すと、表の数字だけ上がる (過学習)**。B の外れ行を直すために語を足す・順位を動かす変更は、この表の改善として数えない。
- 変更の良し悪しは、必ず「**表の外の文**」でも確かめる。このリポジトリに入っている表の外の文: `eval/kanji/kanji-cases.tsv` (212 文。この 2 表と読みの重複 0 を確認済み)、AJIMEE-Bench (`tools/ajimee-eval.py`。200 件、第三者作)、`eval/cases` の日英判定。測るなら、変更の前後で:
  1. `tools/kanji-bench.py` の A・B (悪化 0 を見る)
  2. `tools/ajimee-eval.py` (acc@1 の差と、`--compare` の McNemar)

## 得と損
- 得: 変更ごとに、同じ 193 行を OFF/ON で測り、**どの行が当たり → 外れになったか**が分かる。第三者の表 (AJIMEE) より小さく速い (M4 Max で OFF 約 2 秒、ON 約 8 秒。ビルドを除く) ので、日常の変更で回せる。A は実際の入力 (英単語混じり) の日本語の部分で、左文脈つきの測定になる。
