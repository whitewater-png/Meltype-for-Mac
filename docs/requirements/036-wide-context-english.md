# 036 英単語のすぐ後ろの日本語にも左文脈を渡す (Zenzai ON)

## 背景 (誰が、何に困っているか)
- 観測: Zenzai ON で `excelnohyouwookurimasu` が「excelの票を送ります」、`pythondekaita` が「pythonで描いた」になる。英単語の後ろの短い日本語に、Zenzai へ左文脈が渡らないため。
- 親の実験: `--convert-eval` に英単語つきの左文脈を直接渡すと、比較ベンチ A (日英混在 60 文) の Zenzai ON が 48 → 51 (書いた・表・直った)。ただし Core を通していない実験。

## 今の動き (実物で確かめた)
- `CompositionController.ConversionContext()` は、広い文脈 ON (Zenzai ON かつエンジンが Mozc でない) のとき `WideContextOf(PrecedingForConversion)` を使う。`WideContextOf` は最後の文字が日本語でないと null。
- 同じ入力の中で確定済みの英語 (excel) は `PrecedingForConversion` (= 入力欄の前の文字 + 確定済みの先頭の文節 `FixedText`) に**入る**。ただし最後の文字が英字なので null になる。文脈を記録する偽の変換エンジンで確かめた (`excelnohyouwookurimasu `・`excel nohyouwookurimasu `・`pythondekaita `・`kyouhaexcelnohyouwookurimasu ` のどれも、「英語の直後の日本語」の変換呼び出しの文脈は null。広い文脈 ON/OFF とも同じ)。取り先を変える必要はなく、`WideContextOf` の最後の文字の条件を外せば英語が入る。
- 固定したテスト: `WideContextTests.Context_IsNullAfterEnglish_InSameInput` (今の動き。ON/OFF とも)。

## 測定 (この要件の主な成果)
試した 2 案を、`WideContextOf` を変えたビルドの Core のテスト (使い捨て、コミットしない) で文脈を求め、その文脈を `left_context` 列に入れた TSV を `MeltypeIME --convert-eval --weights zenz-v3.1-small-Q5_K_M` (Zenzai ON、製品と同じ変換経路) で流した 2 段の測定。
- 案 1: 最後の 20 単位をそのまま (英語 + その前の日本語。例 `今日はgoogle`)。
- 案 2: 末尾の英数字の連なりだけ (例 `google`)。
- 比べる相手: 今 (英語の後ろは文脈なし)。表の数字は 当たり→外れ / 外れ→当たり (McNemar の対)。判定は読みの全部の一致 (表記ゆれの許容なし)。

| セット | 件数 | 今 (当たり) | 案 1 | 案 2 | 案 1 の対 (当→外 / 外→当) | 案 2 の対 |
| --- | --- | --- | --- | --- | --- | --- |
| A 日英混在 60 文 (漢字だけ。文脈は製品の切り方) | 60 | 53 | 57 | 57 | 0 / 4 (書いた・表・直った・取る) | 0 / 4 |
| X 自作: コード・コマンド・URL・固有名詞の後ろの日本語 (助詞で始まる) | 45 | 41 | 42 | 41 | 1 / 2 | 1 / 1 |
| B 比較ベンチのかな漢字 120 文の前に、関係のない英単語 (+ 日本語) を置いた最悪の場合 | 120 | 102 | 90 | 90 | **15 / 3** | 15 / 3 |

- A の 4 件は文脈の英単語が文の中身と関係している (excel の表・python で書いた)。親の実験の 48 → 51 (判定を含む数) と同じ向きで、Core を通しても再現した。悪化 0。
- X の変化: 直る = `git commit -m` + を打った (売った → 打った)、`Wi-Fi` + がつながらない (繋がらない → つながらない。案 1 だけ。表記ゆれ)。悪化 = `test.txt` + を直してほしい (ほしい → 欲しい。両案)。コード・URL の英字列を渡しても、ほかに壊れた例はなかった (`https://…`・`README.md`・`sudo apt-get`・`SELECT * FROM users` など)。
- B の悪化は、英単語と関係のない文を後ろに置いた条件で起きる (機嫌が悪い → 期限が悪い、東京に住んでいます → Tokyoに住んでいます、髪を切りに → 紙を切りに、花が咲いている → は長さいている)。実際の打鍵は「excel + の表」のように関係のあることが多いので、これは上限に近い見積もり。ただし、どちらの割合が実際の打鍵で多いかは測れていない。
- B の 15 件のうち B094 (子供→子ども)・B127 (温かい→暖かい)・B152 (野菜→やさい) は表記ゆれに近く、実質は 12 件程度。それでも改善 3 件の 4 倍で、結論は変わらない。X の `test.txt` + を直してほしい (ほしい→欲しい) も表記ゆれに近い。
- AJIMEE (b): 評価表 200 件のうち左文脈つきの 100 件を、広い文脈 ON の Core に通した文脈の文字列は、変更前後で全件同一 (md5 一致)。文脈の末尾が英字のものが 0 件で、変更は末尾が英字のときだけ働くため、AJIMEE の数字は変わらない (構造上)。
- 英単語 1 語だけ (案 2) と、その前の日本語つき (案 1) の差は、A では 0、X で 1 件 (`Wi-Fi`)。20 単位の上限は案 1 のままでよい。
- Zenzai OFF・Mozc: `WideContextProvider` が false を返すので、この変更は届かない (`CreateDefault_WideContextProvider` と、新しいテスト)。

## 判断 (推奨: 見送り)
- 得: Zenzai ON で、助詞で始まる日本語が英単語に続く文 (excelの表を・pythonで書いた) が、A で 4/60 直る。悪化 0。
- 損: 英単語の後ろに、英語と無関係な日本語が続くと、Zenzai が英語の文脈に引きずられて外す。B の最悪の条件で 12.5% (15/120) が悪化し、直るのは 2.5% (3/120)。自作の X でも 1 件の悪化 (`test.txt` + を直してほしい → 欲しい)。
- 実際の打鍵で「関係のある後ろ」と「関係のない後ろ」のどちらが多いかを測る材料がない (A は親が外れ文から選んだ文、X は自作、B は人工)。**悪化が 0 にならず、利得の見積もりも A の選び方に依存する (不確か)** ので、共通の約束 (悪化が出て条件を狭めても消えないとき実装をやめる) に従い、実装は入れない。
- 狭める案も試した。英単語 1 語だけにする (案 2) でも X の悪化は消えない。助詞で始まる読みだけに限る案は、B の助詞始まり 35 文でも悪化 5 / 直る 2 で、消えなかった (「か」始まりの語を助詞と区別できない点も別に問題)。
- 入れたくなったとき: `WideContextOf` の `LanguageOf(text) != false` を `LanguageOf(text) is null` に変えるだけ (測定に使った変更はリポジトリ外の作業フォルダーに保存してある)。効く範囲は広い文脈 ON のときだけ。そのときは、実際の打鍵の記録 (トレースは同意が要る) で関係のある後ろの割合を測ってから決める。
