**基点について (査読 R-P2-1 必須 2 で追記)**: 測定の基点は `669ead5` の Core (このブランチの `f3fcfdf` の親)。そのときの `eval/cases` は 264 件で、本文で「現行ルール」と呼ぶ 231 / 264 はこの時点の値。その後の main (`54a2002`) では `eval/cases` が **310 件** (`mac-protected-spans.tsv` の 46 件が増えた) になり、ルールの正解は **276 / 310 (89.0%)**。元の 264 件の出力は `54a2002` でも 264 件すべて同じ (231 のまま)。`54a2002` での結果は下の「新 main (54a2002) の 310 件での結果」に書いた。

## 結論 (先に)

**no-go 提案。** 仮説のままでは成り立たない。数字は下のとおり、すべて実測 (保存データから計算できる)。

- zenz の尤度で候補を比べると、**英字のままの候補が圧倒的に有利**になり、全面的に置き換えると 264 件の正解が 231 → 最良の P-合計でも 190 に落ちる (ルールが当たっていたものを 53 件壊す)。
- 「ルールより `τ` 以上良いときだけ乗り換える」門を付けると、最良の設定 (前置きなし・合計・τ=8) で 264 件のうち **直した 8 / 壊した 1**。ただし (a) 直した 8 件は `xxxpedia` 系 7 件 + `npx create-next-app` で、実質 2 種類の型に偏っている、(b) τ と方式は同じ 264 件で選んだ (自己採点。約 80 通りの設定の最良)、(c) τ の選択に使っていない新 main の 46 件では **τ=8 で直した 0 / 壊した 2** (`aka/ao`・`a/b`)。310 件全体では直した 8 / 壊した 3。
- 狙いの「途中で切り替わる」型 (`pro|to`・`devtoprod` → `devとprod`) は、候補を全分割に広げると一部だけ当たる (全面置換の P-合計で `pushoyobi`→`pushおよび`・`rdstoredshift`・`やpython` 系 5 件など、copy 方式で `devtoprod`・`apinoerror`) が、ルールが当たっていた例を 100 件以上壊す。門を付けると途中切り替えで直る分はほぼ消え (τ=8 で残るのは `pushおよび` と `site PR`→`して PR` の 2 件)、`Hi there`→`ひ there` のような壊しが 6 件出る。
- 遅延は測るたびに数倍変わる。いちばん速い P 方式でも 1 判定の p95 は 25.0 ms (初版の測定) から 109.1 ms (再測) まで振れ、40 ms 予算に収まるとは言えない。

得は「`pedia` 系の英語を、辞書を足さずに拾える見込み」、損は「全面採用すれば正解率が大きく下がる・遅延が 40 ms 予算に収まらない場合がある・採点のために llama.cpp を直接呼ぶ実装が要る」。得が小さく偏っていて、外部のデータでは得が無く壊すだけなので、製品に入れる根拠にならない。

## 何をしたか

1. **重み**: 取得は不要だった。`~/Library/Application Support/Meltype/models/zenz-v3.1-small-Q5_K_M.gguf` が既にあり、SHA-256 が `ZenzaiModel.swift` の固定値 (`4de930c0…14f6c`) と一致することを確認した。ダウンロードはしていない。
2. **現行ルールの出力**: `dotnet run -c Release -- --expect-all ../../eval/cases out.json` (`669ead5` の `eval/cases` 264 件)。ルールの正解は 231 / 264 (87.5%)、外れは 33 件。`eval/README` の `ascii` と同じ比べ方 (印字可能 ASCII の連続を小文字にした並びが期待と一致) で全件を採点し直した。結果は同じ 231。新 main (`54a2002`) では 310 件・276 (基点の注記を参照)。
3. **補足 14 件**: eval/ には「小文字の人名」「長文」が少ない (人名は `my name is taro` の 1 件、長文は最長 37 文字) ので、`eval/lm-judge/extra/extra-cases.tsv` に作例 14 件を足した (人名 6・pro|to 型 3・長めの混在文 5)。**作者 (私) が書いた作例で、実機で確かめた値ではない。** ルールの正解は 5 / 14。本体の言い換えを含む (`protopedia wo miru` は本体の `protopedia`、`my name is yuki` は `my name is taro` の言い換え) ので、独立したデータではない。
4. **採点器**: `tools/lm-judge/lmscore.cpp`。製品に入っている `llama.framework` (b4846、arm64) に直接リンクし、zenz-v3.1-small Q5_K_M で「前置きのあとに続く文字列」の対数尤度を返す。空白は U+3000、BOS あり、EOS なし (`ZenzContext` と同じ)。CPU のみ、スレッド 10 (この Mac の性能コア数)。Homebrew の新しい llama.cpp は zenz の pre-tokenizer (`gpt2-small-japanese-char`) を読めず使えなかった。採点は決定的: 278 件を別の日時に採点し直した `s3-candidates-rerun.jsonl` は、全スコアの差の最大 0、トークン数・G の出力も一致した。
5. **採点の方式** (候補の文字列 S を次のどれかで採点。漢字変換はしない=かなのまま):
   - U: `<EE00>` の直後に S が続く尤度 / P: 前置きなしで S の尤度 / C: 入力=S、出力=S (写し) の尤度 / G: S を入力にして貪欲復号した出力の確信度
   - 各方式を「合計」と「トークンあたり平均」の 2 通りで比べた (8 通り)。
6. **候補の作り方**: (A) 短い候補表 = {英字のまま, 全部かな (全部が完全にローマ字として読めるときだけ), 現行ルールの出力} の最大 3 つ。(B) 全分割 = 語ごとに「英字区間 / かな区間」の交互の並び (最大 3 区間、かな区間は完全にローマ字として読めるものだけ) の全部。(B) は 224 件 (ルールの外れ全件 + 補足 14 件全部 + 空白で区切った語がすべて 14 文字以下の例。本体は 210 件で、長い語を含む 54 件を外した) で実行。

## 正解率 (実測)

「迷う」の定義: 合成の経路 (`CompositionText.Segments`) からは区切りの確からしさを取り出していない。語単位の日本語/英語の点 (`ScoreEngine.Evaluate(DetectionInput)` が返す `DetectionResult.JapaneseScore`・`EnglishScore`、どちらも public) は取れるが、今回は使っていない。代わりに、**ルールが外した 33 件 (+補足の外れ 9 件) を「迷うケース」の代わり**にし、ルールが当たっていた 231 件を「壊してはいけない対照」にした。つまり本当にルールが迷っている事例の抽出ではない。門の評価は全件にかけて直した/壊したを数えているので、「常に LM を呼び、点差で門をかける」方式の評価としては成り立つ。「ルールが迷ったときだけ呼ぶ」は試していない。

## 遅延・メモリ (実測。注意付き)

条件: M4 Max、CPU のみ (スレッド 10)、製品の `llama.framework` b4846、`tools/lm-judge/lmscore` を単体のプロセスで (azooKey の経路ではない。KV の再利用なし=毎回全文を再計算)。278 件・候補 504 個で採点。所要時間は Python 側の `perf_counter` で測った lmscore とのパイプの往復込みの値 (`s3` が `ms` に記録)。百分位は `lm_judge.py s3lat` で計算する。p95 は線形補間 (`statistics.quantiles(method="inclusive")`、numpy の既定と同じ)。初版の p95 は補間なしの下側 (昇順で `xs[int(0.95n)-1]`) で計算していて、少し小さく出ていた (P 24.9 → 25.0、21 文字以上の P 46.1 → 46.7、G 183.7 → 190.1)。

**1 判定** = その件の候補ぜんぶ (1〜3 個) の合計。278 件のうち 72 件は候補が 1 個 (英字のまま = ルールの出力) で、製品なら LM を呼ばない件。そのため「候補 2 個以上」の 206 件の値も並べる。

| --- | --- | --- | --- | --- |
| P (前置きなし) | 11.8 / 25.0 / 51.3 ms | 14.1 / 26.3 | 46.7 | 6.6 / 12.7 |

- 戦略の予算 40 ms に対して: 初版の測定では P・U は p95 で収まり、C は p95 を超え、G は p50 も超えた。しかし **p95 は測るたびに数倍変わり (P で 25.0〜109.1 ms)、初版以外の測定 (今回の再測と査読者の再測) では P でも p95 が 40 ms を超えた**。「P の p95 は 40 ms 予算に収まる」は、機械が空いているときに限った条件付きの話。打鍵 21 文字以上では、初版と再測の 2 回とも P の p95 が 40 ms を超え (46.7 ms・125.0 ms)、「長文」が狙いなのに長文ほど予算を超える。

## go/no-go

- **no-go (この仮説のままでは)。** 目安 (正解表の「迷ったケース」で改善が一定数以上、かつ追加遅延 40 ms 以内) のうち、改善は `pedia` 系に偏って自己採点、遅延は負荷と長文で超過、のため満たさない。さらに、**別の作業 (1-4a) で作られ main に加わった保護区間 46 件 (τ の選択に使っていない) では、τ=8 は直した 0 / 壊した 2 (`aka/ao`・`a/b`)。新 main の 310 件全体では直した 8 / 壊した 3** (ルール 276 → 281)。補足 14 件の「直した 0」は、届く外れが 1 件しかないので根拠としては弱く、外部データの根拠はこの 46 件のほう。
- もし続けるなら、先に試す価値があるのは (すべて**未検証**): (a) Core のスコア差が小さいときだけ呼ぶ門。語単位の JP/EN 点は `ScoreEngine.Evaluate` (public) から取れるので、合成の経路に手を入れずに、捨てる測定用ドライバで試せる (作業は小さい。ただし短い候補表で届く外れは本体で 15 件しかないので、上限は 231 → 246)。(b) かな区間を漢字に変換したうえでの尤度 (Zenzai 本来の「かな→漢字」の形。今回はかなのまま)。(c) azooKey 内部の候補評価 (`candidateEvaluate` の pass / fixRequired) を使う方式 (内部 API で、Meltype から呼べるかは未確認)。(d) `pedia` 系は、LM を使わず英語の語尾の辞書で直す案 (こちらのほうが安い)。

## 未確認・限界

- **自己採点と最良報告**: 試した設定は方式 8 通り × τ 約 10 通り = 約 80 通りで、その最良を報告している。τ も方式も同じ 264 件で選んだ。
- **τ=8 の「平らな区間」は狭い**: P-合計で英字のままがルールより良い点差の並びは、上から `pedia` 系 7 件 (37.4〜17.6、直)、`anowikipedia` 14.2 (壊)、`uikittoswiftui` 12.9 (どちらでも外れ)、`npx create-next-app` 12.8 (直)、`dottonet` 8.5・`edittopub` 8.1 (どちらでも外れ)。τ=8 のすぐ下に壊す側の `Xnotoukouha` 7.87・`youtubewomiru` 7.60・`hosuthingu` 7.59 がある (τ=7.5 にすると壊すが 3 件増えて 8/4)。逆に外部の 46 件では点差 18.5 の `aka/ao` を壊す。
- **統計**: 直した 8 / 壊した 1 は符号検定 (両側) では p=0.039 に見えるが、8 件のうち 7 件は同じ `pedia` 型で、型でまとめると 2 対 1 (p=1.0)。約 80 通りの多重比較もある。新 main の 310 件では直した 8 / 壊した 3 (p=0.23)。**差は検出できない。** (p 値は二項分布 1/2 での両側の計算。この弱さは no-go の向きを変えない。)
- 補足 14 件は作者の作例で、本体の言い換えを含み、届く外れは 1 件だけ (上記)。「結果を見る前に書いた」ことは外からは確かめられない。
- eval の正解 `ascii` 比べは英字の並びだけを見るので、かなの部分の正しさは見ていない ((B) の段落に例)。
- 直る型が `pedia` 系に偏るのは、`wikipedia` などの語が zenz の学習データに多く出るためかもしれない (推測。確かめていない)。「直る型が学習データの頻出語に偏る」なら、似た型でも頻度の低い語には効かない。
- 遅延は単体の採点器で測った (azooKey の経路ではない)。3 回とも他の作業がある機械で、値は負荷で数倍変わった。M1 級は未測定。GPU 版 (Metal) は使っていない。
- 全分割 (B) は 3 区間までで、かな区間は完全にローマ字として読めるものだけ。Core 本来の区切り (拗音・促音の扱い) とは違う。
- zenz-v3.1-small のみ。左文脈 (EE02 の文脈) を使う v3 の形は試していない。
- `npx create-next-app` (mac-terminal) がコード系アプリでどうなるか (K79) は、`--expect-all` にアプリの種類を渡す引数が無いのでこの道具では測れない (査読 R-P2-1 (非公開) の指摘。`npx` は K79 の一覧外)。
