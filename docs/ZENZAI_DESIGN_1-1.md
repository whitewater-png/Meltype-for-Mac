# 1-1 Zenzai 導入の設計 (2026-10-14 案、査読 R38 反映、前回実験の結果を追記)

戦略計画 (`docs/STRATEGY_2026-10.md`) の施策 1-1。決定済み: 3 = (a) まず実験、4 = (a) 重みは設定で ON にしたときだけ取得。この文書は「実験で何を測り、どうなったら製品に入れるか」と「入れるときの形」を先に決めるためのものです。

## 0. 一言で

Mac 版の変換エンジン azooKey には、同じライブラリの 1 オプションとして **Zenzai (ニューラルかな漢字変換)** が入っています。今はビルドの切り替えごと OFF です。ON にすると、文脈に合う漢字が先頭に来やすくなる代わりに、重み 72〜74 MB の取得・メモリ約 150 MB (azooKey の文書値)・1 キーあたりの遅延が増えます。**まず実験で「速さ・メモリ・精度」を測り、数字で go/no-go を決めます。** 製品に入れる場合は「設定で ON (既定 OFF)」から始めます。

## 1. 今あるもの (コードで確認済み。査読 R38 で訂正)

- azooKey の固定版 (`d59a28e`、2026-09-23) は Zenzai v3 に対応しています (`ConvertRequestOptions.zenzaiMode`、`.v3` は「左文脈」= 入力の前にある確定済みの文をモデルに渡せる)。
- **ただし Zenzai のコードは、SwiftPM の trait (`Zenzai` = GPU/Metal 版、`ZenzaiCPU` = CPU 版) を付けてビルドしないとコンパイルされません。** 今の Meltype は trait 無しなので、代わりの空実装 (`llama-mock.swift`) が入っており、そのまま `.on(...)` を渡すとモデル読み込みで落ちる経路があります。有効にするには `mac/Package.swift` を swift-tools-version 6.1 以上に上げて `traits: ["Zenzai"]` を付ける必要があります (実験の最初の作業)。
- llama.cpp は azooKey が出来合いの `signed-llama.xcframework` (b4846、arm64 + x86_64) を取ってきて使います。IME の実行ファイルは今はリンクしていません。trait を付けると全員の IME がリンクし、`llama.framework` の同梱が必須になります (サイズは未計測。`.build` に残っている 5.6 MB は 2025-04 の古いビルドの残りで、当てになりません)。`build.sh` は置き場の `*.framework` を全部入れるので、**B1 (`otool -L` に出るものだけ同梱する) を先に直します**。
- **左文脈の現状**: カーソル前の文字は、キーを押すたびに日英判定用として `InputController.swift` が読んでいます (未確定の文字が無いときだけ、UTF-16 で 20 単位まで)。その文脈は `Converter.clauses(for:context:)` まで届いていますが、**今は使わずに捨てています**。渡すには、変換オプションを要求ごとに作る (今は `let` で 1 つ)・結果キャッシュのキーに文脈を足す (今は読みだけがキー)、の 2 つの変更が要ります。長さは自前で切らず azooKey の `maxLeftSideContextLength` に任せます。
- 計測の道具: `MeltypeIME --bench` (変換の速度・一致の計測)。精度の正解表はまだ無く、`eval/cases` は日英判定用 (変換エンジンは偽物) なので、**かな → 漢字の正解表を新しく作る必要があります**。
- 重み: Hugging Face `Miwa-Keita/zenz-v3-small-gguf` (72.3 MB) / `zenz-v3.1-small-gguf` (73.9 MB)。
- **前回の実験 (10/12、Cline セッション、ブランチ `exp/zenzai-eval`、削除済み) の結果を復元しました** (作者の手元のフォルダー、非公開: 計測ログ、70 文と 96 文のコーパス、`ZenzaiEval.swift`・`make-corpus.swift` の復元版、重み zenz-v3.1-small Q5_K_M 73.9 MB)。要点:
  - CPU 版 (trait `ZenzaiCPU`) は動いた。**GPU 版 (`Zenzai`/Metal) は llama.cpp b4846 の bf16 カーネル読み込みで落ちる** (この Mac、Xcode 無し。原因は推測のまま)。
  - 精度: 手作り 70 文で 47 → 58 (上限 3)、技術文書 96 文で 32 → 42。悪化は 2/70、6/96。**上限 3 で頭打ち** (5 でも増えない)。
  - 遅延 (CPU 版、M4 Max): 1 キー平均 5 ms → 15〜18 ms、95% で 30〜37 ms。メモリは未計測。
  - 左文脈は渡していない。96 文の正解表は読みを自動生成したので表記ゆれが多く、絶対値は当てにならない (相対差のみ)。
  - 重みのライセンスは CC BY-SA 4.0 → 取得方式でも THIRD-PARTY-NOTICES に表記が要る。
  - **前回の数字は未検証として扱う** (リョウさんの指示)。計測は 1 回ずつで、読みの自動生成・表記ゆれ・コードの正しさを誰も査読していない。今回はまず同じ 70 文・96 文で再計測して再現するかを確かめ、**go/no-go は今回の数字だけで決める**。計測コードは Opus が査読する。

## 2. 実験 (ブランチ `exp/zenzai-1-1`、製品コードは触らない)

前回の結果を踏まえ、今回の実験は **(1) GPU 版を動かす (llama.cpp の版上げか bf16 無効化。無理なら CPU 版で確定)、(2) 左文脈あり/なしの精度差、(3) メモリ、(4) 正しい正解表での精度** の 4 点に絞ります。速さの CPU 版の数字は前回のものを使い、GPU 版が動けば測り直します。

| 測るもの | やり方 | go の目安 |
| --- | --- | --- |
| 速さ | `--bench` に Zenzai ON/OFF を足し、**1 キーあたりの合計** (予測・ライブ変換・文節候補の最大 3 回の呼び出しの合計。読みが違うのでキャッシュは効かない) の中央値と 95% を出す。`inferenceLimit` 1 / 3 / 5、trait `Zenzai` (GPU) と `ZenzaiCPU` の両方 | 95% が **80 ms 以下** (OFF の今の値も並べる)。GPU 版が本命、CPU 版は参考 |
| メモリ | ON 前後の phys_footprint (アクティビティモニタの「メモリ」。RSS だと Metal 側が見えにくい) | 増分 **250 MB 以下** (文書値 150 MB に余裕) |
| 精度 | かな → 漢字の正解表 **200 文** (下記) で第一候補の一致率を ON/OFF で比べる。左文脈あり/なしも分ける。同じ文どうしの対応比較 (McNemar 検定) を添える (200 文で 5 ポイント = 10 文なので、偶然かどうかを見る) | ON が OFF より **5 ポイント以上**良く、悪化する文が 1 割以下。参考: 作者の公開ベンチは 1,745 文で約 6.5 ポイント改善 |
| 日英判定への影響 | `eval/cases` 264 件 (Core 側。変換エンジンは別なので変わらないはず) | 変化 0 |
| 起動・安定 | モデルは最初の変換要求の中で同期的に読まれる (先に読ませる公開 API は見当たらない)。最初の変換が何秒止まるか、別スレッドで先に読ませられるか (KanaKanjiConverter はスレッドセーフでないので要検証) | 止まる時間が分かる。無理なら「ON にした直後の 1 回は待つ」を仕様にする |
| 同梱サイズ | trait 付きでビルドした Meltype.app の増分 (llama.framework + C++ 連携分) | 記録のみ (go/no-go には使わない) |

正解表 200 文の作り方 (決定: 公開文のみ): 前回の手作り 70 文 (同音異義語など、人が読みを付けたもの) を引き継ぎ、ニュース・技術文・会話の 130 を足す (Haiku に「読みと漢字と左文脈」の組を作らせ、Sonnet が別に検算、私が 20 文抜き取り)。`eval/kanji/*.tsv` (読み・期待・左文脈の 3 列)。リョウさんの文は正解表に入れず、実機 2〜3 日の体感で補います (希望があれば、リポジトリに入れない私的な表を別に作れます)。

費用の目安: Sonnet 実装 2〜3 回 + Opus 査読 1 回 (計 $15 前後の目安、サブスク内)。期間は前回の資産 (trait 対応の差分・計測コード・70 文) を復元できたので **1〜1.5 週間**。GPU 版の問題が深ければ CPU 版で判断します (前回の数字では CPU 版でも go の目安の範囲内)。リョウさんの実機作業: ON の dev ビルドで 2〜3 日ふだん使いし、体感 (遅さ・落ちた回数・変換の良し悪し) を 5 行で。

## 3. 製品に入れるときの形 (go のとき)

1. **設定**: 「設定」タブに「Zenzai (ニューラル変換、実験的)」のスイッチ。**既定 OFF**。ON にすると重みの取得が始まり、取得中は OFF のまま動きます。
2. **重みの取得**: 設定で ON にしたときだけ、HTTPS で 1 回。URL・サイズ・SHA-256 をアプリに固定 (改ざんや別ファイルを読ませない)。保存先 `~/Library/Application Support/Meltype/models/` (0700)。失敗したら OFF に戻して理由を表示。既存の更新確認 `Updater.swift` の作法 (使い捨てセッション・通信先の許可リスト・転送先の制限) に揃えます。**Hugging Face の `resolve/` は CDN に転送されるので、転送先ホストを調べて許可リストに入れる** (未調査)。取得するプロセスは IME 側 (Updater と同じ) にし、辞書アプリの設定スイッチは「ON にしたい」の印を立てるだけにします。`mac/README.md` の「通信」節に 1 種類として追記。
3. **変換**: `Converter.swift` の `zenzaiMode` を `.on(weight:, inferenceLimit:, requestRichCandidates:, personalizationMode: nil, versionDependentMode: .v3(…左文脈…))` に (`personalizationMode` は既定値が無いので明記)。推論上限は実験で決めた値。左文脈は §1 の文字列 (20 単位。必要なら読む長さを増やすのは別件)。要求ごとのオプション生成とキャッシュキーの変更を含む。
4. **安全弁**: 重みの読み込みに失敗・1 キーの変換が 300 ms を超えることが連続したら、そのセッションは自動で OFF にしてログに 1 行。
5. **配布**: `llama.framework` を同梱 (OFF の人にも増える。サイズは実験で計測)。重みは同梱しません。Homebrew cask・pkg・zip の 3 経路とも手順の変更は無し。B1 の直しを含む。
6. **文書**: README の「できること」に 1 行、「プライバシー」に通信の 1 種類追加、`KNOWN_LIMITS` に「Intel Mac は未確認・GPU が無いと遅い可能性」。実験の数字は `docs/ZENZAI_EXPERIMENT_2026-10.md` に残します (本家が追随しても「測った」実績は残る)。

## 4. 守ること・リスク

| リスク | 対応 |
| --- | --- |
| 通信が増える (「打った内容を送らない」が売り) | 送るのは重みの取得要求だけ。打った内容は一切送らない。ON にした人だけ、1 回だけ。方針文に明記 |
| 重み (GGUF) を llama.cpp が解析する = ネイティブコードが外部ファイルを読む | SHA-256 で固定した 1 ファイルしか読まない。IME プロセス内で動くので落ちると IME が落ちる → 安全弁と、必要なら Phase 3-3 (別プロセス化) |
| trait で全員のビルドが変わる (OFF の人にも llama がリンクされる) | OFF なら読み込まない (コード上は mock と同じ経路にならないことを実験で確認)。サイズ増は計測して README に書く |
| Intel Mac・古い macOS | 配布物は arm64 のみなので Intel は対象外のまま。macOS 13〜15 は未確認と明記 |
| azooKey の版上げが必要になる | 固定版が v3 対応済みなので当面不要。v3.2 (右文脈) を使うなら版上げ (別件) |
| 本家も同じことができる | そのとおり。先行価値は「左文脈 × 日英判定の統合」と「計測結果の公開」 |
