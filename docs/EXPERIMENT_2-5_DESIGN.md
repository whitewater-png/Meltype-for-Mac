## 1. 本家 #286 の主張 (事実の整理)

出典: <https://github.com/yksr-melt/Meltype/issues/286> (`gh issue view 286 --repo yksr-melt/Meltype` で本文を取得。2026-10-10 作成、状態 OPEN、コメント 0 件、ラベル「提案」「優先: 低」、起票者は本家の作者で、下書きは Claude Code)。

- 題: 「打鍵の間隔で英語か日本語かを見分けられるか測る (仮説)」。**実装の提案ではなく、作る価値があるかを測る提案**。「測って差が無ければ閉じます」と書いてある。
- 困りごと: 今の判定は打った文字と前後の文字だけを見る。`mata`・`kore`・`tama`・`you`・`sure` のような両読みの語は文字だけでは決まらず、前の文で判定し直しても #230 のような「英文の続き」と「日本語の文中の製品名」を見分けきれない。
- 特徴量の案 (仮説 2 つ):
  1. 言語を切り替える所 (英単語の後ろの空白 → 次の語の最初のキー) で間が空く。
  2. 英単語 (指が綴りを覚えている) は速く均等、ローマ字は違うリズム。
- 例 (数字は仮): `hello ␣(80ms) mata` = 英文の続き / `GitHub ␣(600ms) mata` = 止まって日本語に切り替えた。
- 測り方 (3 段): ①設定 ON のときだけ判定ログに「キー間隔 (ms)」だけを足す (文字は残さない・ローカルのみ) → ②自分で直した語 (外れた判定) と直さなかった語で間隔分布に差があるか → ③差があるときだけ `ScoreEngine` の手がかりに足すかを考える。
- 本家自身が挙げた懸念: 間隔は人・キーボード・疲れで大きく変わる (人ごとの基準との差で見る必要)。キーの時刻をどこまで正確に取れるかは、Windows (キーボードフック・TSF)・Mac・Linux の**3 つとも確かめる対象**として挙げている。記録は数値だけで、打った文字と結びつけて保存しない。
- 本家はまだ測っていない (コメントも結果も無い)。**効果の有無は誰も確認していない**。

### 1.1 本家の制約とこの設計の違い

本家は「判定の記録に間隔**だけ**を足す」「打った文字と**結びつけて保存しない**」と書いている。この設計は、間隔のほかに、長さの区分・判定・文脈の点・規則の種類・直したか (§5.1) も残す。これらは打った文字から決まる値なので、本家の制約から外れる。

外れる理由: 英語とローマ字は綴りが違うので、間隔の差は「文字の並びの違い」だけで説明できてしまう (§3.4)。文字を残さずにこの交絡を統制するには、文字から決まる要約 (列挙値) を残すしかない。間隔だけでは、間隔が判定に**上乗せ**できるかを確かめられない。

代わりに取る対策: 残すのは両読みの語の行だけ・項目は数値と少数の列挙値だけ・長さと間隔の個数は区分にまとめる・ミリ秒は 10ms に丸める (§5.1)。本家に結果を返すときは、この違いを添える。

### 2.3 時刻の取り方の結論

- **`event.timestamp` を使う**。Core が呼ばれた時刻 (`MeltypeSession.cs:419`) には、IME の処理の遅れが混ざる。この遅れは、直前に変換を待ったか (= 直前が日本語か) で変わりうる。すると H1 (語の前の間) に、言語と結びついた偽の差が出る。だから Core の時刻では足りない。
- 渡し方: 既存の `meltype_handle_key` の引数は変えず、Swift が `handleKey` の直前に時刻を渡す関数 (例: `meltype_set_key_time(handle, double)`) を**足す**。任意の関数を足したときに ABI 版数を上げなかった先例がある (`Exports.cs:80`・`:98`、「ABI 版数は上げていない (古い本体には無く、その場合 Swift 側は 0 として扱う)」)。古い本体に無ければ記録しないだけで、入力は変わらない。版数を上げるかは実装の査読で決める (上げるなら 12。1-1 Zenzai などと取り合いになる)。
- `event.timestamp` の実際の精度は、段階 1 の実装の最初に確かめる (未確認)。

## 3. 仮説・単位・ラベル・比べる土台

### 3.1 仮説 (事前に固定)

- **H1 (主)**: 両読みの語の区間の最初のキーの直前の間 (`gap`) は、自動の判定が外れて利用者が覆した区間で、外れなかった区間と違う。#286 の仮説 1 (切り替える所で止まる) に当たる。語の最初のキーを打つ前は、まだその語の判定が画面に出ていないので、「外れた表示を見てためらった」という逆向きの因果が入らない。
- **H2 (従。go の判断には使わない)**: 区間の中のキー間隔の中央値・ばらつき。#286 の仮説 2。打っている間に区間ごとの判定 (英字のまま / かな) が表示されるので、外れた表示を見て指が止まると、H2 は「意図」ではなく「外れへの反応」を測ってしまう。この交絡があるので、記述だけにする。

### 3.2 単位 (1 行)

- 1 行 = **確定したときの `CompositionDetector` の区間 (segment) 1 つ**で、その区間の英字が `IsAmbiguousWord` を満たすもの (`CompositionText.Segments(final: true)`、`src/Meltype.Core/Composition/CompositionText.cs:763`。区間は `CompositionSegment(IsEnglish, Kana, Raw, Protected)`、同 `:22`)。`kyouhamata` のように 1 回の変換ボックスに日本語と両読みの語が混ざっても、両読みの区間だけが行になる。
- 間隔はその区間に入ったキーだけで計算する。`gap` は、区間の最初のキーと、その前に Core が受けたキーとの差。間にフォーカスの移動 (`activateServer`) やクリック (`InputController.swift:136-140`) があれば `gap` は「不明」にする。
- 人ごとの基準 `base` は、**その時点より前**の区間内のキー間隔の直近 200 個の中央値 (メモリの中だけで持つ。IME を起動してから 50 個たまるまでは行を作らない)。その日の中央値のような、後の語を使う値は使わない (交差検証で情報が漏れるため)。
- 判定の強さが手動 (`DetectionLevel.Manual`) のときは行を作らない (自動の判定が無いので、外れが定義できない)。

### 3.3 ラベル: 言語を覆したときだけ

「直した」は、**自動の判定と違う言語を利用者がはっきり選んだ**ときだけにする。Core にはその通り道が **3 つ**ある (`fix` の値は §5.1)。

1. `CompositionController.LearnLanguage` (`:2518-2541`。`:2369` で、確定後の F6 の変換ボックスでないときに呼ぶ):
   - 英数の表示 (F9/F10) で確定し、自動の区間に日本語があった → **日→英** (`l_en`)。`LearnLanguage` が覚えるのは区間が 1 つのときだけ (`:2529-2532`。2 つ以上だと、どの語を英語にしたかったか決められないので覚えない、`:2531`)。ラベルも同じにする: 区間が 1 つならその行に `l_en`。2 つ以上なら、その確定の両読みの行で自動が日本語だったものを `mix` (覆したことは分かるが、どの語かは決められない) にする。
   - かなの表示 (F6〜F8) で確定し、自動の区間に英語があった → **英→日** (`l_ja`)。学習と同じく、自動が英語だった両読みの行すべてに立てる (`:2533-2535`)。
   - 判定の強さが手動で Tab で英字にした (`:2536-2539`) → 手動は行を作らないので使わない。
2. 確定後の F10 / F6 (`TryToggleLastWord`、`CompositionController.cs:2626-`。呼ぶのは `MeltypeSession.cs:432-437`、結果の `SessionResult.Toggle` は `:20`・`:41`)。確定から 3 秒以内 (`LastWordTrustMs = 3000`、`:2574`) だけ効く。
   - F10 = **日→英** (`t_en`)。入力欄を書き換えた時点 (`TryToggleLastWord` が true を返す) で立てる。Swift が書き換えを確かめられずに取り消したとき (`CancelToggle`、`:2717-`。FFI は `meltype_cancel_toggle`) は、ラベルも `none` に戻す。学習と同じ条件 (確定が日本語の区間 1 つだけ、`learnable`、`:2666`) のときその行に立て、区間が混ざった確定では `mix` にする。区間は 1 つでも `learnable` でない (変換して文節が 2 つ以上になった、`JapaneseWord: false`) ときも、Core は覚えないので `mix`。
   - F6 = **英→日** (`t_ja`)。F6 は変換ボックスを開くだけで、Esc 1 回で元の語に戻せる (`:1442-1444`)。だから **F6 を押した時点では立てない**。開いたボックスを確定し、Core がそこで日本語として覚えたとき (`:2375-2378`。暗黙の確定 (フォーカス移動・クリック) と 1 音確定のあとは覚えない) に、元の確定の英語の区間 (`toggle.Previous.Raws.English`) の行に立てる。Esc で取り消したら `none`、暗黙の確定か 1 音確定 (下の決まり) で終わったら `mix`。このボックスの確定では `LearnLanguage` を呼ばないので (`:2369`)、二重には数えない。
3. 変換の候補で言語を選び直す (`Learn()`、`:2952-2964`。呼ぶのは変換して確定したとき `:2365`、変換していないが固定した文節がある確定 (`fixedOnly`) `:2368`、一部の文節だけ確定したとき `:398`・`:1597`。ローマ字の再変換では呼ばない、`:2365`。1 音確定のあとは何もしない、`:2954`):
   - 日本語と判定した語の候補から、打ったままの英字を選んで確定した → **日→英** (`c_en`。`:2955-2959`、コメントに「F10 と同じ」)。
   - 英語と判定した語で日本語の候補を選んで確定した → **英→日** (`c_ja`。`:2960-2964`、コメントに「F6 と同じ」)。
   - `c_ja` の条件 (`:2961`) は、候補を選び直したか (`Changed`) を見ない。Shift+Space の変換 (`:988-992` の `StartConversion(preferJapanese: true)`、`:1619-1621`) では、英語の文節の最初の候補が日本語になるので、候補を選ばずにそのまま確定しても `c_ja` が立つ (Core もそこで日本語として覚える)。利用者が自分で日本語を求めた操作なので、この場合も陽性に含める。
   - 学習としては「はっきり選んだ」扱いにならない (`explicitChoice` は既定の false。`LanguageMemory.cs:327` の説明に「変換の候補から選んだだけなら false」)。それでも利用者が自分で言語を選び直した点は F10/F6 と同じなので、ラベルにする。内訳 (`l_*`・`t_*`・`c_*`) は件数で報告する。
   - `Learn()` の単位は変換の文節で、行の単位 (判定の区間) と違う。文節の打った英字と同じ英字の両読みの区間が、その確定の中に 1 つだけあるときにその行に立てる。1 つに決まらなければ、その確定の両読みの行を `mix` にする。

主な解析の陽性は `l_*`・`t_*`・`c_*`。`mix` と `recommit` は主な解析から除き、件数だけ数える。

陽性は、**Core がその確定で言語を覚える場合**にそろえる。覆したことは分かっても、Core が覚えない確定 (語を 1 つに決められない・F10 で `learnable` でない・下の 1 音確定) は `mix` にする。
- 1 音確定 (Shift+↓。`_firstSoundCommitted`、`:2481`) をした変換ボックスの確定では、Core は言語を覚えない (`LearnLanguage` `:2520`・`Learn()` `:2954`・確定後の F6 のボックス `:2375`)。この確定に言語を覆す操作 (英数/かなの表示・候補の言語の選び直し。上の 1 と 3 の条件に当たるもの) があれば、その確定の両読みの行は `mix`、なければ `none`。
- 確定後の F6 で開いたボックスを 1 音確定で終えたときは、元の確定の英語の区間 (`toggle.Previous.Raws.English`) の行を `mix` にする。

ラベルにしないもの:
- 候補の選び直しのうち、言語が変わらないもの (漢字の選び直し。上の 3 の 2 つの場合に当たらないもの)。ローマ字の再変換。F6〜F10 を押しても言語が変わらないもの (自動でも日本語だった区間をカタカナ・半角にしただけ、など。`LearnLanguage` もこの場合は覚えない)。Tab での変換の開始や予測の選択。
- 自動の確定し直し (`CorrectPreviousCommit`、`CompositionController.cs:2906-2949`) は利用者の判断ではないので、`fix = recommit` として別に記録し、主な解析から除く。

ラベルの漏れ (測れない外れ): Backspace で消して打ち直す、英数/かなキー (`InputController.swift:161-178`) で切り替えて打ち直す、直すのが面倒で放置する。これらは「外れなかった」に混ざる。シミュレーション (§5.4) では、本当の外れの 30% が直されない (`miss = 0.3`) と置いた。

行を書く時点: `l_*`・`c_*` は確定のときに決まる。確定後の F10/F6 は確定の 3 秒後には効かないので、行は、確定から 3 秒たつか、次のキーで `_lastWord` が消えるまでメモリに置き、ラベルが決まってから書く。確定後の F6 でボックスを開いたときは、そのボックスが確定か取り消しになるまで置く (3 秒を過ぎても)。

### 3.4 比べる土台 (間隔を足す前のモデル)

各行に、判定が使った材料と結果を列挙値で残す。

| 項目 | 値 | 出どころ |
| --- | --- | --- |
| `pos` | 変換ボックスの最初の区間か (`s`) / 途中か (`m`) | 区間の位置 |
| `len` | 区間の文字数の区分 `1-2`/`3`/`4`/`5`/`6+` | `Raw.Length` |
| `cb` | 前の文脈の点 -1/0/1/2 | `BeforeScore` (`CompositionDetector.cs:310`) |
| `ca` | 後ろの文脈の点 -1/0/1 | `Score(after)` (`:592`) |
| `rule` | 判定を決めた規則の種類 `mem`/`ctx`/`spell` | 下の反実仮想で決める |
| `auto` | 自動の判定 `en`/`ja` | `CompositionSegment.IsEnglish` |
| `lvl` | 判定の強さ `A`/`B`/`C` (積極的・標準・慎重) | `DetectionLevel` |

`rule` の決め方: `IsEnglishSpanCore` に理由を返させると判定のコードに手が入るので、そうしない。「判定を調べる」機能 (`DictionaryManagement.ExplainDetection`、`src/Meltype.Core/Composition/DictionaryManagement.cs:187-255`) と同じく、条件を 1 つ外して区分けし直し、その区間の判定が変わるかを見る。
- 学習を外す (`Memory = null`) と変わる → `mem` (学習で決まった。`:688`)
- そうでなく、前後の文脈を「不明」にすると変わる、または (自動が日本語なら) 前後を「英語」にすると変わる → `ctx` (文脈の点で決まった。`:779`。「判定を調べる」の `before-english`・`after-english`・`before-none`・`after-none` と同じ置き換え)
- どちらでも変わらない → `spell` (綴りだけで決まった)

区分けし直すのは、**フラグ ON・確定のとき・両読みの区間があるとき**だけで、確定 1 回につき 2〜3 回。判定の結果は変えない。

主な解析のモデル (事前に固定): ロジスティック回帰。土台 = `pos`・`len`・`cb`・`ca`・`rule`・`auto`・`lvl` の one-hot。土台 + H1 = それに `log(gap / base)` (5000ms で頭打ち) を 1 つ足す。H2 の特徴は主な解析に入れない。

### 3.5 学習の影響 (2 回目以降の直しが減る)

- 覆した語は `LanguageMemory` に「はっきり選んだ」(`explicitChoice`) として覚える (`LanguageMemory.cs:324-327`。変換の候補で選び直した `c_*` は、はっきり選んだ扱いではないが、同じく覚える)。次からは `:688` の学習で決まるので、**同じ語の 2 回目以降の外れは減る**。陽性は、新しい語の最初の 1〜2 回に集まりやすい。直しの件数は、日数に比例して増えるとは限らない (始めの週が多く、だんだん減る)。
- 例外: よく使う日本語 (`sushi`・`kyouha`) は、はっきり英字にしても 1 回では覚えない (2 回ルール、`LanguageMemory.cs:58-73`、確定後の F10 の知らせ `CompositionController.cs:2669`)。この語は 2 回目も直すことがある。
- 両方の言語で使う語 (`mata`・`kore`・`you`) は、覚えた向きが別の文脈で外れる。`rule = mem` で直した行は「**学習の後も残る外れ**」で、間隔が最も役に立ちうる場所。件数を週ごとに数えて報告する (§5.5)。これが少なければ、成功しても得は小さい (§8)。
- 語を残さないので、同じ語の繰り返しは見分けられない。繰り返しは行どうしの独立を崩し、実効的な件数を減らす (§5.4 の注意)。

## 4. 段階 0: 決まった文の書き写し (Meltype のコード変更なし)

目的: 自然なログ (段階 1。プライバシーの費用がかかる) の前に、安くて安全な条件で H1 の信号があるかを見る。

- 方法: 両読みの語 (`mata`・`kore`・`sure`・`you`・`tama` など T 語) を、**同じ英単語 + 空白の後ろ**に置き、英語のつもり (英文の続き) と日本語のつもり (切り替え) の 2 つの文に入れる。各語を各文脈で R 回、順番を混ぜて書き写す。Meltype は ON のまま。
- 記録: ローカルの HTML ページ (ネットに出ない) で `keydown` の `event.timeStamp` と `event.code` を取る。打つ文は秘密ではないので、文字も記録してよい。ラベル (どちらのつもりか) は文から分かる。
- 確かめること 0a (未確認): Meltype の変換中にも、ブラウザーが `keydown` を時刻つきで出すか。出なければ、段階 1 の Swift の計測を先に作るか、段階 0 をやめる。
- 判定 (事前に固定): 語ごとに `log(gap)` の「日本語のつもりの平均 − 英語のつもりの平均」を出し、T 個の平均の**片側 95% 下限 > 0** なら「H1 の信号あり」。
- 件数 (シミュレーション。`stage0_sim.py` (リポジトリの外。手元のみで公開していない)、seed 20261015、各 4000 回): 仮定は、語ごとの基準 N(0, 0.3)、語ごとの効きの違い N(0, 0.1)、打鍵ごとのばらつき sigma (log の単位。実測していない)。δ は本当の差 (log。0.18 は約 1.2 倍、0.3 は約 1.35 倍)。

| T 語 × R 回 (1 文脈) | sigma | δ=0 (誤って go) | δ=0.1 | δ=0.18 | δ=0.3 |
| --- | --- | --- | --- | --- | --- |
| 24 × 4 | 0.4 | 0.048 | 0.471 | 0.874 | 0.999 |
| 24 × 4 | 0.6 | 0.047 | 0.288 | 0.617 | 0.942 |
| 32 × 4 | 0.4 | 0.051 | 0.582 | 0.954 | 1.000 |
| 32 × 4 | 0.6 | 0.050 | 0.357 | 0.737 | 0.986 |

  → **32 語 × 2 文脈 × 4 回 = 256 語**にする (20〜30 分を 2 回の見込み。未実測)。1.35 倍の差なら、ばらつきが大きくても 0.98 以上で見つかる。1.2 倍だと 0.74〜0.95。
- 得: 安い。文字を残してよいので安全。同じ綴りを両方のつもりで比べるので、綴りの交絡が根本から消える。ラベルが正確 (弱いラベルの問題が無い)。
- 損: 書き写しなので、考えながら打つときの止まり方 (H1) が自由作文と違うかもしれない。文を読む間が「切り替えの間」に混ざる (英語と日本語の文で、読む量を揃える)。被験者はリョウさん 1 人。段階 0 で信号があっても、自然な文章で外れを予測できるとは限らない (それを確かめるのが段階 1)。

### 5.1 残すもの (1 行 = 両読みの区間 1 つ。数値と決まった列挙値だけ)

### 5.2 残さないもの・記録しない場面

- **打った文字・語・前後の文字 (surroundingText)・候補・読み**: 個人情報・秘密情報になる。
- **アプリ名 (bundle ID)・ウィンドウ名・URL**: 何を見ているかが分かる。アプリの種類も残さない (下のとおり一般アプリだけを記録するので要らない)。
- **キーごとの間隔の並び**: 打鍵時間から内容を推定する攻撃が知られている。区間ごとの要約だけにする。要約でも推測の余地は 0 ではないので、端末内の 0600 に置き、外へ送らない。
- **両読みでない区間**: 行を作らない。数字・記号・大文字を含む語は `IsAmbiguousWord` の時点で除かれる (`CompositionDetector.cs:521`)。
- **英数 (Direct)・Meltype 全体の OFF**: Swift の `handle` には判定が無い。決めるのは Core (`MeltypeSession.cs:424-429`、`Direct || !AppEnabled || !_settings().Enabled` で、変換ボックスに入れる前に返す)。そこで行は **Core が変換ボックスを確定したとき**にだけ作る。英数・OFF のキーは変換ボックスに入らないので行にならない。§7 のテストで確かめる。
- **コード系アプリ (エディター・ターミナル)**: 丸ごと記録しない。Core は `AppProfile.Code` で分かる (`Exports.cs:312-319` が Swift に `1` を返す。Swift の `AppKind.code`、`NativeCore.swift:158-164` にターミナルも含む)。理由: ターミナルの `sudo`・`ssh` のパスワードは、ターミナルが秘匿入力にしない限りふつうの入力として Core に入る (`KNOWN_LIMITS.md` K74)。損はコード系アプリのデータが無くなることだが、主な対象は一般アプリの文章なので受け入れる。
- **秘匿入力中**: Swift の `handle` が Core を呼ぶ前に素通しする (`InputController.swift:146`) ので、行は作られない。加えて、Swift は時刻と一緒に「記録してよい」の印 (秘匿入力でなく `appKind == .general`) を渡し、Core は**確定のきっかけになった呼び出しの印**を行と一緒にメモリに持つ (ファイルには書かない)。書くときは、その印と書く瞬間の `IsSecureEventInputEnabled()`・`appKind` の両方を確かめ、どちらかが外れたら捨てる (トレースの `:80` と同じ形)。行は確定から 3 秒ほど (F6 のボックスはそれ以上) 遅れて書くので、書く瞬間の状態だけでは打った瞬間の状態にならないため。秘匿入力になったときに Swift が未確定の文字を確定する経路 (`InputController.swift:147`) は印を渡さないので、行を作らない。
- **正確な時刻・端末名・利用者名**。

残るリスク: 一般アプリの中で、秘匿入力にしないパスワード欄 (Web アプリが独自に作った欄など) で、両読みの英単語 1 語のパスワードを Meltype の日本語モードのまま打つと、その区間の間隔の要約が残る。除けない。英字だけのパスフレーズも同じ。コード系の判定はアプリの一覧 (`MacCodeApps`) とアプリ別設定によるので、一覧に無いターミナル・ブラウザーの中のターミナル (Web の SSH コンソールなど)・利用者が「一般」にしたターミナルでは記録される。そこでパスワードを打てば同じことが起きる (残るのは長さの区分と間隔の要約)。間隔の要約は、指の癖 (行動の生体情報) になる。

### 5.3 同意と運用の決まり

1. 既定 OFF。ON にする手段は `defaults write io.github.yksr-melt.inputmethod.Meltype MeltypeTimingLog -bool true` だけ (ドメインは `mac/Resources/Info.plist:10`。`MeltypeTraceIMK` と同じ流儀。設定画面には出さない)。
2. ON にする前に、リョウさんが §5.1〜§5.3 を読んで承諾し、§5.6 の判断事項 (§5.6.1 記録を自動で消すか・§5.6.2 記録の上限・§5.6.3 読み取りを OS の層で止めるか。3 つとも条件 0 の前にまとめて決める (2026-10-15 の決定)) を決めておく (承諾は会話で明示的に取り、日付と選んだものを実験メモに残す。決めなければそれぞれ既定の A)。**エージェントが勝手に ON にしない**。承諾を取るときは、本文より先に、次の要点をこの形で見せる:
   - **上限: 陽性 300 件・12,000 行 (約 2MB)・8 週の、どれか先に来たもの。前の案 (1MB・約 6,000 行) の約 2 倍の打鍵の要約を残しうる**。1MB に戻すと、陽性の割合が 5% 未満なら 300 件に、約 3.3% 未満なら 200 件に届く前に止まり、「結論なし」に落ちやすい (割合は未測定)。**下げることも選べる** (§5.6.2)。
   - 記録は既定では自動で消さない。消すのはリョウさんが確認したあと (§5.6.1)。
   - エージェントの読み取りの拒否は `cat` などには効くが、Python のスクリプトが開くファイルには効かない。既定ではその経路は指示だけで守る (§5.3-8・§5.6.3)。
   - 残るのは数値と列挙値だけ。秘匿にしない欄のパスワード・一覧に無いターミナルでの間隔の要約は除けない (§5.2)。
3. **期限**: IME は 2 つの値を自分の defaults に持つ。(a) `d` の起点 = 最初に書いた日 (承諾し直しても変えない)。(b) 期限の起点 = 承諾した時刻。**書き込むたびに**、(b) から 14 日と (a) から 8 週 (§5.4 の上限) を確かめる (IME は何日も動き続けるので、起動時だけの確認では止まらない)。どちらかを過ぎたら書かない。**止めるだけで、ファイルは消さない**。延ばすときは、リョウさんの承諾を取り直してから (b) だけを書き直す。ファイルはそのまま追記を続けるので、承諾し直しが遅れても集めかけの記録は消えない (止まっていた間の行が無いだけ)。承諾し直しのときに見せるのは件数 (全行・陽性) だけで、解析の途中の結果は見ない。
4. **表示**: ON の間は入力メニューに「打鍵間隔の記録中」を、止まった後も**ファイルが残っている間**は「打鍵間隔の記録が残っています (消去…)」を出し続ける。**既定では自動で消さない**。消すのはリョウさんが確認したあと (9)。自動で消す案は §5.6.1 の判断事項。
5. **保存先**: `~/Library/Application Support/Meltype/experiment/timing-log.jsonl`。ファイル 0600、ディレクトリ 0700。書き手は回さず、一時ファイルも作らないので、記録のファイルはこの 1 つだけ。バックアップの除外を ON の前に確かめられるよう、手順を「ディレクトリを 0700 で作る → `tmutil addexclusion <ディレクトリ>` → `tmutil isexcluded <ディレクトリ>` で除外を確かめる → `defaults write` で ON」の順にする。IME はディレクトリを作らない。書く前にディレクトリの `isExcludedFromBackup` を読み、ディレクトリが無いか、除外されていなければ書かない。`rm` で消しても Time Machine の過去のバックアップには残るため。
6. **上限** (回さない): 次のどれかで書くのをやめる。(a) 主な解析の対象の陽性 (§5.5 (b)) が 300 件に届いた (それ以上は集めない)。(b) 12,000 行 (約 2MB)。(c) 8 週 (3 の (a) から)。止まったら、入力メニューに理由 (「目標の件数に届きました」「記録がいっぱいで止まりました」「期間が終わりました」) を出す (気づかずに期間を延ばす判断を誤らないため)。止まったあとの扱いは §5.4 (陽性の件数で決める)。1MB (約 6,000 行) にしないのは、陽性の割合が 5% 未満だと 300 件に届く前に止まり、未測定の割合しだいで「結論なし」に構造的に落ちるため。12,000 行なら割合 2.5% 以上で (a) が先に来る。増えるのは同じ種類の要約 (数値と列挙値) だけ。ただし残す要約の最大は前の案の約 2 倍になるので、(b) を下げるか (例: 1MB に戻す) は §5.6.2 の判断事項にし、承諾のときに最初に見せる (2)。

   - **仕組みで守れる範囲** (Claude Code の公式の文書 <https://code.claude.com/docs/en/permissions>・<https://code.claude.com/docs/en/sandboxing> で確認、2026-10-15。実機では試していない):

### 5.4 件数と判定の規則 (シミュレーションで決めた)

査読で、元の規則 (「AUC の増分 ≥ +0.03 かつ区間が 0 を含まない」・170 件) は、本当に +0.03 の効果があっても go の確率が半分ほどで頭打ちになると指摘された。規則と件数を、自分で回したシミュレーションで決め直した。

シミュレーション: `power_sim.py` (リポジトリの外。手元のみで公開していない。numpy 2.0.2、seed 20261015、ブートストラップ 400 回)。結果の生の出力は同じ場所の `power_v2.txt`。仮定 (実データではない):
- 1 行 = 両読みの区間。28 日 (一部 14 日) に分かれる。陽性の割合 10%。本当の外れのうち 30% は直されない (陰性に混ざる)。
- 外れやすさ = 日ごとの揺れ (log-odds で N(0, 0.3)) + 文字と文脈から分かる情報。土台の特徴量はその情報を 8 区分にした列挙値 (Mac の土台が列挙値なので)。土台の AUC は約 0.65 と約 0.80 の 2 通り。
- 間隔の特徴 = 外れなら gamma だけずれる + 基準で割っても残る日ごとの速さ (N(0, 0.15)) + 打鍵ごとのばらつき (N(0, 1))。母集団の ΔAUC (40 万行で当てはめ、別の 40 万行で評価) は、土台 0.65 で gamma 0.4 → 0.030、0.3 → 0.018。土台 0.80 で gamma 0.7 → 0.032。
- 交差検証は**日ごとにまとめた 5 分割** (ランダムに分けない)。区間は**日ごとに取り直すブートストラップ**。

分かったこと 1: **5 分割の予測を 1 つにまとめて AUC を出す方式は使えない**。効果が無いとき (gamma 0) に、誤って go になる率が片側 5% のはずが 7.1%〜18.5% になった (土台 0.80・陽性 300 で 18.5%。理由は推測: 土台が列挙値なので、分割ごとの当てはめの違いがまとめたときの土台の順位を崩し、連続値の間隔の特徴が見かけ上役に立つ)。**分割ごとに ΔAUC を出して平均する方式**では 3.1%〜4.9% (1000 回ずつ) で、5% を超えなかった。

分かったこと 2 (分割ごとの平均、片側 95% 下限 > 0 で go。各 400 回):

| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.65 | 0.030 | 0.378 | 0.535 | 0.708 | 0.828 | 0.935 | — |
| 0.65 (14 日) | 0.030 | — | — | 0.735 | — | 0.948 | — |

- 元の規則 (推定 ≥ 0.03 かつ両側 95% 下限 > 0) は、同じ方式で陽性 300 でも 0.470〜0.522 だった (査読の指摘と同じく、半分ほどで頭打ち)。
- 参考: 係数の検定 (間隔の係数を、日ごとにまとめた頑健な標準誤差で片側 z > 1.645) は、効果なしで 4.0%〜5.9%、土台 0.65・ΔAUC 0.030・陽性 100 で 0.960 と、ずっと検出力が高い。ただしこれは「関連がある」で、「判別が上乗せされる」ではない。

決めたこと (事前に固定。後から動かさない):
- **意味のある最小の効果**: ΔAUC = 0.03 (件数の見積りにだけ使う。判定の規則には入れない)。
- **判定の規則 (主)**: H1 の特徴 1 つを足したときの、日ごとにまとめた 5 分割の**分割ごとの ΔAUC の平均**の、日ごとのブートストラップ (2000 回) による**片側 95% 下限 > 0** なら「間隔は判別に上乗せできる」。
- **ブートストラップの方式 (シミュレーションと同じに固定)**: 日を 5 つの分割に割り当て、交差検証の予測 (土台と、土台 + H1) を **1 回だけ**作る。ブートストラップでは**当てはめ直さない**: 日を復元抽出して行を集め、その行で分割ごとに ΔAUC を出し (陽性と陰性の両方がある分割だけ)、平均する。2000 回の 5 パーセンタイルを下限とする (`power_sim.py` の `one_run` の `by_fold` と同じ。シミュレーションは 400 回)。効果なしで誤って go が 3.1〜4.9% という性質は、この方式で確かめたもの。当てはめ直す方式に変えるなら、その方式でシミュレーションをやり直してから変える。
- **件数**: 主な解析の対象 (§5.5) の**陽性 300 件**で 1 回だけ解析する (途中で覗いて止めない)。上の仮定で、土台 0.65・ΔAUC 0.030 の検出力 0.935。300 にしたのは、仮定に入れていない依存 (同じ語の繰り返し・学習による時間の流れ、§3.5) で実効的な件数が減る分の余裕。
- 期間の上限は 8 週 (14 日の期限を 3 回まで承諾し直す)。記録が止まったら (§5.3-6 の陽性 300 件・12,000 行 (§5.6.2 で下げたらその行数)・8 週のどれか)、陽性の件数だけで次を決める: 300 件 → 解析。200〜299 件 → その件数で 1 回だけ解析し、件数と検出力を添える (200 件で 0.828)。200 件未満 → 「結論なし」とし、「差なし」とは書かない。上限を上げて集め直すことはしない (上げるなら別の設計にして、リョウさんの承諾を取り直す)。
- 係数の検定は補助として報告する。主の規則が通らず係数だけが通ったときは、「関連はあるが判別の上乗せは確認できない」として段階 2 に進まない。
- H2 は記述だけ。複数の比較で go を決めない (主は H1 の 1 つ)。

#### 5.6.1 記録を自動で消すか (取り消せない操作)

記録ファイルを消すことは取り消せない (Time Machine の対象外にしているので、消すと戻せない)。だから設計では決めず、リョウさんの判断事項にする。

**消す範囲 (どの案でも同じ)**: `~/Library/Application Support/Meltype/experiment/timing-log.jsonl` の、**決まったパスのファイル 1 つだけ**。
- ディレクトリごと消さない。ワイルドカード・`rm -r` を使わない。
- パスがシンボリックリンクなら消さない (リンクの先も消さない)。ふつうのファイルでなければ消さずに知らせる。
- 学習データ (`languages.json` など)・ユーザー辞書・設定 (defaults)・同じディレクトリのほかのファイルは対象外。`LearningData.ClearAll` は呼ばない (逆向きの「学習データをすべて消去」が記録も消すのは、確認の画面に書いたうえでのこと。§5.3-7)。
- エージェントが消す場合も、リョウさんの OK を会話で取ってから、このパス 1 つだけを消す。

| 選択肢 | 中身 | 得 | 損 |
| --- | --- | --- | --- |
| **A (既定・おすすめ)** 自動では消さない | 期限・上限で記録を止めるだけ。ファイルが残っている間、メニューに「打鍵間隔の記録が残っています (消去…)」を出し続ける。集計を終えたら、エージェントが消すことを提案し、消すのはリョウさんが確認したあと | 集計の前や承諾し直しの前に、実験のデータを失わない。消す時点をリョウさんが選べる | 消し忘れると、打鍵の要約が端末に残り続ける (初回査読 R4 (b) の懸念)。メニューの表示と、集計の報告の最後の提案で減らす |
| B 自動で消す | 8 週の上限 (`d` の起点から 56 日) から N 日 (例: 30 日) たったら、IME が上の 1 ファイルだけを消す。14 日の期限ごとには数えない (承諾し直しの途中では消さない)。N はリョウさんが承諾のときに選ぶ。メニューに「あと何日で消えます」を出す | 消し忘れが無い | 集計がその日までに終わっていなければ、実験のデータを失う (陽性 300 件の集め直し)。取り消せない処理を IME に持たせることになる (実装と査読の手間、消す範囲を誤る危険) |

おすすめ: **A**。消すのは取り消せないので、消す時点はリョウさんが持つほうがよい。ファイルは数値と列挙値だけで約 2.1MB 以下 (12,000 行。§5.6.2 で下げればそれ以下)、端末内の 0600 で Time Machine の対象外なので、残っている間の害は限られる。B の得 (消し忘れが無い) の大部分は、メニューの表示と提案で取れる。

決めないとどうなる: **A のまま動く**。記録は止まっても消えず、メニューの表示が出続ける。消すのはリョウさんが確認したときだけ。段階 1 が go にならなければ記録自体が作られないので、決めた内容は使われない (決めるのは条件 0 の前。§5.6 の頭)。

#### 5.6.2 記録の上限: 12,000 行 (約 2MB) にするか

前の案は 1MB (約 6,000 行) で、再査読 R2 の P3 で 12,000 行 (約 2.1MB) に上げた (§5.3-6)。取り消せない操作ではないが、残す打鍵の要約 (行動の生体情報) の量の最大が約 2 倍になるので、リョウさんの判断事項にする。どの案でも、陽性 300 件・8 週で止まるのは同じで、止まったあとの扱い (§5.4: 300 件で解析・200〜299 件は件数と検出力を添えて解析・200 件未満は「結論なし」) も変えない。

| 選択肢 | 中身 | 得 | 損 |
| --- | --- | --- | --- |
| **A (既定・おすすめ)** 12,000 行 (約 2.1MB) | 陽性の割合が 2.5% 以上なら 300 件が先に来る。200 件には約 1.7% 以上が要る | 陽性の割合 (未測定) が低めでも、「結論なし」に落ちにくい | 残す要約の最大が B の約 2 倍。陽性 300 件で先に止まれば、実際の行数は割合しだいで少なくなる |

おすすめ: **A**。陽性の割合は未測定で (条件 0 でも目安しか出ない)、低いと B では結論が出ないまま期間が終わる。増えるのは同じ種類の要約 (数値と列挙値) だけで、端末内の 0600・バックアップの対象外・陽性 300 件で先に止まる、は変わらない。

決めないとどうなる: **A (12,000 行) で動く**。途中で下げることはできる (その時点で行数が新しい上限以上なら、そこで止まる)。上げることはしない (§5.4)。段階 1 が go にならなければ、決めた内容は使われない (決めるのは条件 0 の前。§5.6 の頭)。

#### 5.6.3 エージェントの読み取りを OS の層で止めるか (生ファイルを読むスクリプトを誰が動かすか)

§5.3-8 のとおり、Claude Code の読み取りの拒否は `cat` などは止めるが、Python のスクリプトが開くファイルは止めない。集計のスクリプトも条件 0 のスクリプトも Python なので、`python3 -c` で中身を表示する経路は、拒否だけでは止まらない。OS の層で止めるには sandbox が要るが、sandbox はエージェントが動かす集計スクリプトの読み取りも止める。そこで、スクリプトを誰が動かすかと合わせて決める。対象は実験の記録 (`timing-log.jsonl`) と、条件 0 で読む学習ファイル (`languages.json`)。

| 選択肢 | 中身 | 得 | 損 |
| --- | --- | --- | --- |
| **A (既定)** 今のまま | Claude Code の `permissions.deny` と指示。スクリプトはリョウさんに見せたうえで、エージェントが動かす | リョウさんの手間が少ない (スクリプトを見て OK するだけ) | `python3 -c` などで読む経路は指示だけで守る。Hermes は拒否の設定も無く、指示だけ |
| **B (おすすめ)** 生ファイルを読むスクリプトはリョウさんが動かす | エージェントはスクリプトを書いて見せる。リョウさんが自分の端末 (エージェントの外) で動かし、出た集計値だけを会話に貼る。`permissions.deny` も置く | エージェントが生ファイルを読む正当な理由が無くなる (読む操作はすべて決まりに反するものになり、見分けやすい)。Hermes にも Claude Code にも同じに効く。設定を変えないので、ふだんの作業に影響しない | リョウさんの手間 (条件 0 で 1 回、段階 1 の件数の確認を数回、解析 1 回)。仕組みではなく運用なので、エージェントが決まりを破れば読めるのは A と同じ |
| C B に加えて Claude Code の sandbox を ON | `sandbox.enabled: true`、`filesystem.denyRead` に実験のディレクトリと `languages.json`、`allowUnsandboxedCommands: false`。これらのスクリプトを `excludedCommands` に入れない | Claude Code の Bash からは、Python でも OS が読み取りを止める | Hermes (端末の道具は sandbox の外) には効かない。sandbox を ON にすると、Bash の書き込みとネットが既定で絞られ、ふだんの作業 (ビルド・`gh` など) が止まりうる (影響は確かめていない)。置く設定ファイルの範囲 (利用者全体か、このリポジトリだけか) も決める必要がある。空白を含むパスのパターンが合うかは未確認 (§5.3-8 の手順で試す) |
| D sandbox を ON にし、集計スクリプト 1 本だけを `excludedCommands` で外に出して、エージェントが動かす | C の設定に、スクリプトを動かすコマンドだけを足す | リョウさんの手間が A と同じ | `excludedCommands` はコマンドの文字列で合わせるので、エージェントがスクリプトの中身を書き換えれば、外で何でも読める。スクリプトの書き換えを止める組み方 (置き場所を書き込みの外にするなど) は確かめていない (未確認)。守りは A とあまり変わらない |

おすすめ: **B**。Python の経路が残る根本は、エージェントに生ファイルを読ませる正当な場面があることで、B はそれを無くす。Hermes を含むどのエージェントにも同じに効き、設定を変えないのでふだんの作業を壊さない。Claude Code だけで扱い、ふだんの作業への影響を確かめられるなら、C を足す価値がある (Hermes には効かない)。どの案でも、漏れたときに出るのは数値と列挙値の要約だけで、打った文字は含まない (§5.1。ただし条件 0 の `languages.json` には打った語が入っている)。

決めないとどうなる: **A のまま動く** (今までの設計)。`python3 -c` などの経路が指示だけで守られていること (§8 の損) を受け入れたことになる。条件 0 も段階 1 も、リョウさんの OK なしには動かない。決めるのは条件 0 の前 (2026-10-15 の決定)。

- エージェントが生ファイルを読めば外部送信になる。Claude Code の読み取りの拒否は `cat` などは止めるが、Python のスクリプトが自分で開くファイルは止めない (公式の文書。§5.3-8)。集計のスクリプトも条件 0 のスクリプトも Python なので、`python3 -c` で中身を表示する経路は、既定 (§5.6.3 の A) では指示だけで守ることになる。Hermes には拒否の設定自体が見当たらない。OS の層で止める sandbox は Claude Code の Bash にしか効かず、ふだんの作業を絞りうる。おすすめの B (生ファイルを読むスクリプトはリョウさんが動かす) でも、エージェントが決まりを破れば読めることは変わらない (§5.6.3)。漏れても、記録の中身は数値と列挙値の要約だけで打った文字は含まない (§5.1)。条件 0 の `languages.json` には打った語が入っている。
- 記録は既定では自動で消さない (§5.6.1 の A) ので、消し忘れると打鍵の要約が端末に残る (メニューに出し続ける・Time Machine の対象外にして減らす)。逆に自動で消す B にすると、集計の前に実験のデータを失う筋がある。
- 段階 1 の実装コスト (Core・Swift・テスト・集計スクリプト) と、FFI に関数を足すことの本家との同期のコスト。版数を上げるなら 1-1 (Zenzai) などと取り合いになる。
- 段階 2 まで進むと、人ごと・機器ごとの校正が要り、誤爆時の害は今より増えうる。

no-go にする場合: リョウさんが記録を取りたくない、または Phase 2 の他の項目に手が要る場合。

## 9. 未確認として残るもの

- `event.timestamp` の実測の精度と単位。IME の処理の遅れが言語によって違うか (§2.3 の前提)。
- 段階 0 の 0a (Meltype の変換中にブラウザーが `keydown` を時刻つきで出すか)。
- 両読みの語の直しの頻度 (条件 0 で目安を出す)。学習による減り方。
- シミュレーションの仮定 (陽性の割合 10%・直されない外れ 30%・日ごとの揺れの大きさ・打鍵のばらつき) は実データではない。同じ語の繰り返しと時間の流れは入れていない。
- `rule` の反実仮想の区分けし直しにかかる時間 (確定のたびに 2〜3 回)。
- IKDD の言語。§6 の出典 (査読では開き直していない)。
- 段階 0 の所要時間 (20〜30 分を 2 回は見込み)。
- 陽性の割合 (10% は仮定)。12,000 行で陽性 300 件に届くには 2.5% 以上、200 件には約 1.7% 以上が要る (6,000 行なら 5%・約 3.3%。§5.6.2)。
- Claude Code の読み取りの拒否は、組み込みの道具・`cat` などの Bash のファイルのコマンド・リダイレクトには効き、Python などのスクリプトが自分で開くファイルとファイル名を書かない `grep -r` には効かない。これは公式の文書で確かめた (2026-10-15)。実機では試していない。
- 空白を含むパス (`Application Support`) のパターンが、`permissions.deny` と sandbox の `denyRead` で合うか (文書に書かれていない。§5.3-8 の手順で、仮のファイルで試す)。sandbox を ON にしたときのふだんの作業への影響。sandbox の中で集計スクリプトの書き換えを止める組み方 (§5.6.3 の D)。
- Hermes に特定のパスの読み取りを拒否する設定があるか (見当たらなかった。網羅ではない)。Hermes の端末の道具を OS の層で止める手段があるか。
