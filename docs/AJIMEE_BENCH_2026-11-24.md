# AJIMEE-Bench の計測 (2026-11-24、Zenzai ON/OFF)

目的: Zenzai (ニューラル変換) の良化を、**自分たちで作っていない正解表**で示す。`eval/kanji` (212 文) は 142 文を LLM が作っているので Zenzai に有利な可能性が残る (`ZENZAI_EXPERIMENT_2026-10.md` §信頼度の注記)。第三者作の AJIMEE-Bench で測って、その疑いを 1 段減らすのがねらい。

## 何を測ったか
- **対象**: Mac 版のかな → 漢字変換。製品と同じ `MeltypeConverter.clauses(for:context:)` を呼ぶ (`mac/Sources/MeltypeIME/ConvertEval.swift` を新規、`main.swift` に 1 行)。日英判定 (`eval/cases` 839 件) は測らない — 軸が違うので `eval/cases` とは**並べて**使う。
- **正解表**: AJIMEE-Bench (https://github.com/azooKey/AJIMEE-Bench) の `JWTD_v2/v1/evaluation_items.json` **200 件**。日本語 Wikipedia 入力誤りデータセット v2 のテストデータから `kanji-conversion_a` (かな漢字の変換の誤り) を含む項目を 200 件サンプリングし、100 件を左文脈付き・100 件を文脈なしに分けたもの (README の構築手順)。**許容解は複数列挙** (平均 2.1 個)。
- **ライセンス**: 正解表のデータは CC-BY-SA 3.0 なので**リポジトリに同梱しない**。実行時に取って `~/.cache/meltype/ajimee/` に置く。評価の式は本家 `utils.py` が CC0 1.0 なので、同じ式 (acc@1 = 第一候補が許容解に含まれるか / MinCER = 許容解のうちの最小の CER) を `tools/ajimee-eval.py` に書き写した (Levenshtein は自前実装。標準ライブラリだけで動く)。
- **計測機**: Apple M4 Max、macOS 27.2.1、36 GB。ビルドは `swift build -c release --package-path mac`。実測に使う木は `origin/main` の **`9f28603826e238de1f07f23623c963ec75593108`** に下の 3 ファイルを足したもの (コードは `feature/ajimee-bench` の `aaea22f` にコミット済みだが、**実測の木は `9f28603` + この 3 ファイル**で、コミットの木は `20736db` + この 3 ファイルなので同一ではない) で、成果物の `MeltypeIME` (10,321,368 バイト) は MD5 **`5c4c164cf51a07d8e16a935cbfa4e03b`**。ON/OFF は**この 1 つのバイナリ**を 1 回ずつ走らせた。手元の作業 HEAD (`feature/ajimee-bench` の `20736db`) は `9f28603` の祖先なので、下の数字は `20736db` のビルドではない。Zenzai は CPU 版、重みは zenz-v3.1-small Q5_K_M (73,871,968 バイト、SHA-256 `4de930c06bef8c26…`)。`--weights` は製品の `ZenzaiModel` と同じ検査 (サイズ・SHA-256 をアプリに固定した値と比べる) を通したので、製品が使うのと同じ重みである。

## 判定式の修正 (2026-11-24、この日の午後にやり直した)
採点側の `tools/ajimee-eval.py` に、AJIMEE の入力をカタカナからひらがなへ直す式 (`katakana_to_hiragana`) のバグがあった。カタカナは `-0x60` で寄せるが、**中音符 `・` (U+30FB) もカタカナの範囲 (U+30A1..U+30FF) に入っている**ので、`・` が U+309B の濁音記号 `゛` に化けていた (長音符 `ー` U+30FC は U+309C の半濁音記号 `゜` に化けるので、そちらは最初から除外していた)。期待値側の `・` と食い違い、**Zenzai ON で 7 件 / なしで 3 件**が「外れ」に落ちていた。`・` をそのまま通すように直して両方をやり直した。

- **変えたのは採点式だけ**で、変換エンジン (`MeltypeConverter` / Core) と Swift 側は未変更。上の MD5 のバイナリはそのままだ。
- 修正前の値 (OFF 85 / ON 158) はこの誤判定を含んでいた。下の表が修正後の確定値。

## 判定 (設計 `ZENZAI_DESIGN_1-1.md` §3.6 の目安)
- **精度**: +38.5 pt (目安 +3 pt 以上)、悪化 2/200 = 1 % (目安「悪化 1 割以下」) → **満たす**。主に見る数字は**左文脈なしの +37.0 pt** (下の「左文脈の形」の注)。
- **速さ**: この測定の p95 113 ms は目安 80 ms を**超える**。ただし母数が違う (下の「速さの注記」) → 目安の合否は製品経路で測り直してから出す。

## 注記 (数字の読み方)
1. **この表は「変換の誤りを含む項目」を選んだ表** (README の構築手順)。一般的な文章の精度ではないので、OFF の 44.0 % は「製品が 4 割しか当たらない」という意味ではない。ON/OFF の**差**を見る表。
2. **速さの注記**: ここは「1 行の読みをまとめて 1 回変換」したときの 1 行あたりの時間。製品は 1 キーごとに予測 + 確定なので、`ZENZAI_EXPERIMENT_2026-10.md` 段階 3 の製品経路の p95 61 ms (上限 3) とは測り方が違う。査読 R39 の「速さは製品経路で測り直す」はここでも残る。遅い行は長い行 (id 1236: 読み 117 文字で ON 202 ms / OFF 66 ms、id 1858: 100 文字で 164 ms)。読み 60 文字以上の 26 件に絞ると ON の平均 103.6 ms / OFF の平均 38.1 ms。ON の外れ 35 件のうち 10 件 (29 %) が読み 60 文字以上で、表全体では 26/200 (13 %) なので、外れは長い行に寄っている (外れ 35 件の読み長は平均 44.9 / 中央 39 文字。表全体の読み長は平均 29.1 / 中央 22 文字)。
3. **左文脈の形**: この計測は `context_text` をそのまま渡す (文脈あり 100 件の文脈長は平均 12.8 文字・最大 67 文字)。製品は Core が**同一文の中の最大 10 文字**に切る (`LEARNING_CONTEXT_REVIEW_2026-11-06.md` §3) ので、「左文脈あり 80/100」は製品の数字ではない。製品と同じ切り方で測るなら、その切り方を計測機にも入れる。
4. **入力長の制約**: 本家は「入力長の制約がある手法」用に `splitted_input_for_limited_input_length` (33 件) を用意している。ここでは**分割せず全文を渡した** (azooKey 側は長さの制約がないので比較の母数を揃えるため)。Zenzai 側は長い行で打ち切りが出うる。
5. **学習語・ユーザー辞書は空** (一時フォルダーを使い、利用者の `~/Library/Application Support/Meltype/azooKey` に触らない)。製品は学習語が乗るので ON/OFF ともに数字が変わる。
6. **分布の重なり**: 正解表は日本語 Wikipedia 由来。Zenzai が学習で似た分布 (Wikipedia 系の文章) を見ている可能性は消せないため、ON 側が上ぶれしている可能性が残る (ZenZai の学習データの構成は今回の計測で確認していない)。`eval/kanji` のときと同じ注意。
7. **再現**: 修正後は main のビルド (`5c4c164c…`) で ON/OFF を 1 回ずつ (OFF 88 / ON 165)。修正前の 2 回一致 (実験木と main のビルドで OFF 85 / ON 158) は中黒の誤判定を含むので、参考値として残す。

## Meltype-Flash (appipinopi/Meltype-Flash) との突き合わせ (参考)
同じ Mac で、競合の Meltype-Flash が公開している正解表を**我々のエンジン**で測った。目的は「どちらが上か」ではなく、**共通の物差しを持てるか**を見ること。

- **彼の 40 件表**: `rust/ai/data/ime-qa-accuracy.json` (40 件、同音異義語 24 / 文脈付き長文 16)。判定は `rust/ai/examples/accuracy.rs` が**完全一致 1 回だけ** (正解は 1 語、許容解の列挙は無い)。Top1 / Top3 / Top8 のランクと MRR を出し、`tools/compare-rust-benchmarks.py` の `accuracy_gate` が **Top1 ≥ 80 % / Top3 ≥ 90 % / Top8 ≥ 95 % + 前回リリースからの悪化なし** を通す。入力は読み ≤ 160 (UTF-16 個)、左文脈 ≤ 80 文字。
- **我々のエンジンでの測定** (同じ `5c4c164c…` のバイナリ、`--items` で彼の表を AJIMEE と同じ形 (`question.reading → input` / `question.context → context_text` / `answer → expected_output[0]`) に変換して流す):

| 区分 | acc@1 (完全一致) | MinCER の平均 | 1 行 p50 / p95 / 最大 |
|---|---|---|---|
| Zenzai なし | 23 / 40 (57.5 %) | 12.9 % | 8.4 / 19.1 / 20.0 ms |
| Zenzai ON | 37 / 40 (92.5 %) | 1.9 % | 18.9 / 28.5 / 34.2 ms |

  外れ 3 件: `しこうをかさねる` (我々は「施工」、正解は「試行」)、`しょうかいさきをたずねる` (我々は「紹介先」、正解は「照会先」)、`こどもたちがこうえんであそんでいる` (我々は「子ども」、正解は「子供」)。3 件目の 1 件は**表記規範の違い**で、語の取り違えではない — 許容解を 1 個しか置かない判定だと、こういうケースが誤りとして数えられる (AJIMEE の測り方なら「子ども / 子供」は両方許容解になりうる)。
- **彼の公開している数字** (リリース本文、v2.0.0-rc1 = 2026-11-23 公開): 10,000 文で**正解率 76.76 %** (7,676 / 10,000、ベースライン 44.14 %)、P50 5.47 ms、RSS 10.66 MB、169.5 文/秒。カテゴリ別は複合語 97.10 % / 英日混在 95.90 % / 固有名詞 78.90 % / 基本変換 77.10 % / 実用文章 76.84 % / 特殊入力 59.15 % / 難読・ネットスラング 42.00 %。
- **並べるときの注意** (並べないと同じ数字が意味を失う): ① 母数が違う (彼の 10,000 文 vs 彼の 40 件表 vs 我々の AJIMEE 200 件)。② 引擎が違う (rc1 は「AI 推論ゼロ・Pure-Rust / ルールベース」をうたう一方、40 件表は `shunti` エンジンを `download` 付きで測る。つまり**公開されている精度は 2 系統**で、引擎もコーパスも違う)。③ 計測機が違う (彼の P50 5.47 ms はマシン不明。我々は M4 Max)。④ v2.0.0-rc1 のリリースアセットは Linux / Windows のだけで **macOS 版が無い**ので、彼の最新をこの Mac で測れていない (上の表はあくまで我々のエンジンを彼の表で測ったもの)。
- **ライセンス**: 彼のリポジトリは GPLv3 (我々と同じ)。AJIMEE-Bench は CC-BY-SA 3.0 で GPLv3 に一方向互換なので、出典を書けば同梱は可能。ただし今の運用 (実行時に取得、同梱しない) を続ける。

## ON の外れ 35 件の候補表 (リポジトリの外)
`~/.hermes/profiles/umi/cache/meltype-eval/candidates/misses.tsv` に 35 件を出した (カテゴリ / id / CER / 左文脈 / 読み長 / 層の切り分け / 期待側 / 出力側 / なしの第一候補)。AJIMEE 由来の本文を含むので**リポジトリには置かない** (同梱するなら CC-BY-SA の出典表記が必要)。

- 内訳: 同音異義語 1-2 文字 **21 件** / 3-5 文字 **6 件** / 区切り・その他 **8 件**。中黒の誤判定を直したので、修正前の 42 件 (28 / 6 / 8) から 35 件に減った。`candidates/classify.py` の正規化は `・` を削るので、記号・数字の部類 (A) は 0 件で、中黒の差は B / D に混ざっている (外れの行のうち `・` を含む行は修正前 10 件 → 修正後 3 件)。
- 層の切り分け: **Zenzai が劣化させた 2 件** (なしは正解) / **ON もなしも同じ誤り 5 件** / **なしは別の誤り 28 件**。
- この 28 件が「辞書の語彙不足」か「ランキングの問題」か分けられない理由は、`ConvertEval.swift` が**第一候補しか残さない**から。候補を N 個出す `--top N` を足せば、正解語が候補に並んでいるか (= ランキング) / 並んでいないか (= 語彙) を機械的に判定できる。

## 再現手順
```bash
cd Meltype
swift build -c release --package-path mac
python3 tools/ajimee-eval.py --binary mac/.build/release/MeltypeIME --out <DIR_OFF>
python3 tools/ajimee-eval.py --binary mac/.build/release/MeltypeIME --weights <重み.gguf> --out <DIR_ON> --no-download
python3 tools/ajimee-eval.py --compare <DIR_OFF>/rows.tsv <DIR_ON>/rows.tsv --out <DIR> --labels なし,ON
```
正解表は最初の 1 回だけ `~/.cache/meltype/ajimee/evaluation_items.json` に取得する (以降は `--no-download`)。`--weights` を付けない走りが Zenzai なし。成果物は `<DIR>/report.md` (外れの一覧) と `<DIR>/rows.tsv` (行ごとの生データ)、`--compare` の `<DIR>/compare.md` (悪化・改善の行)。

Meltype-Flash の 40 件表で測るには、`rust/ai/data/ime-qa-accuracy.json` を上の形 (`index` / `input` / `expected_output` / `context_text`) に変換した JSON を `--items` に渡す (40 件の読み・正解・文脈は元のまま、変換は形だけ)。
