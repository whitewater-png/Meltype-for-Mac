## 要件定義書の候補
既存の要件 001〜014 (と PR #20 の 016・#23 の 018・#24 の 019・#25 の 020・#26 の 021)、10-24〜11-19 の文書の候補、`eval/cases/` と突き合わせた。11-05 の文書に本家 #1301 (Markdown の記号 `` ` ``・`*`・`-`・`>`・`+`) が載っているが、そのときの候補は「コードを書くアプリ」での話で、かなの直後の `*` と `@`・`#` の幅の食い違いは扱っていない。

1. **かなの直後の記号の幅をそろえる (`*` が全角 `＊` になり、`@`・`#` は半角のまま)** (本家 #2093) — scope: core
   - 背景: fork で `kyouha*` → `きょうは＊` なのに `sorewa@` → `それわ@`・`nanika#` → `なにか#` と、記号によって全角・半角が分かれる。作者も「全角半角を気にしなくていい」ことを強みに挙げている。
   - minimum 要件: まず、かなの直後の ASCII 記号 (`*`・`@`・`#`・`&`・`%`・`+`・`=` など) をどの幅にするかを人が決める (協力者の言う `「」` のように全角が意図のものは除く)。決めた幅に `*` をそろえる。
   - 完成条件の案: 正解表に `kyouha*`・`nihongo*desu`・`sorewa@`・`nanika#` などを足し、直す前は外れ・直した後は当たる。Markdown の `*強調*`・箇条書きの `* ` の形 (11-05 の #1301) が変わらないことを守る行も足す。Core 全件通過、eval-compare の broken 0。判定ロジックに触るので、査読員が境界例を作って base と比べる。

2. **ユーザー辞書の読みにローマ字・ハイフン (`pi-a-ru`・`isyu-`) を入れたときの扱いを決める** (本家 #2088) — scope: core
   - 背景: 本家で、ローマ字の読みは登録できるのに、打っても候補に出ないという報告。fork の読みのそろえ方もローマ字をかなに直さないように読める (推測)。
   - minimum 要件: fork で同じことが起きるかを Core のテストで確かめる。起きるなら、(a) 登録時にローマ字の読みをかなに直す、(b) 登録時に「読みはかなで」と弾く、のどちらにするかを人が決める。
   - 完成条件の案: `UserDictionary` のテストに「読み `pi-a-ru` で登録 → `piaru` / `ぴあーる` を打って出る (または登録が理由付きで弾かれる)」を足し、直す前は赤・直した後は緑。既存の読み (ひらがな・カタカナ) の登録・取り込みのテストは全部通る。設定・学習データのファイル形式 (`userdict.txt`) を変えるなら CLAUDE.md §5 で止めて相談する。

3. **本家 11-20 の誤判定の形を、かなのまま (英字にしない) で正解表に守る行として足す** — scope: core (正解表とテストだけ。判定ロジックは変えない)
   - 背景: `sitaidesu`・`amatte`・`chomatte`・`yappane`・`kakikomiera-`・`2nitime` は、本家では漢字の選び方の問題だが、英字を含む形 (`mat`・`era`・`time`) でもある。fork では今どれも日本語 (かな) になるが、正解表に同じ形の行が無い。019・020 と同じ考え。
   - minimum 要件: 上の形を、今の出力 (`したいです`・`あまって`・`ちょまって`・`やっぱね`・`かきこみえらー`・`2にちめ`) で `eval/cases/` に足す。漢字の形は測れないので扱わない。
   - 完成条件の案: 足した行が今の main で当たる。わざと崩した版で外れることを一度確かめる。Core 全件通過、eval-compare の broken 0。
