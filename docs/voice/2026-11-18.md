## 要件定義書の候補
既存の要件 001〜014 (と PR #20 の 016・#23 の 018・#24 の 019)、10-24〜11-17 の文書の候補、`docs/USAGE.md` と突き合わせた。

1. **文の途中の `zl`・`zk` を、見えている形のまま確定する** (本家 #2013) — scope: core
   - 背景: `hogezl` を打つと `ほげzl` と見えているのに、Enter・Space で `ほげぞ` が入る (`zk` も同じ)。見えている形と入る形が違うのは、文の途中の `zl` を矢印にしない設計 (`CompositionText.cs` 139 行) とは別の経路 (打ち間違いの補正と推測) によるもの。
   - minimum 要件: 文の途中の `zl`・`zk` は、確定したときに見えていた `zl`・`zk` のまま入る (または、人が決めれば `→`・`↑` にする。本家の報告者と Apple の日本語入力は矢印を期待)。先頭の `zl` → `→`、`zlib`・`kyouhazlib` が英字のままの動きは変えない。どちらに揃えるかは人が決める。
   - 完成条件の案: 正解表に `hogezl`・`hogezk`・`kyouhazlnaru` を外れる行として、`zl`→`→`・`zlib`・`kyouhazlib`・`hogezh` を守る行として足し、直す前は外れ・直した後は全部当たる。Core 全件通過、eval-compare の broken 0。打ち間違いの補正に触るので、査読員が境界例 (`zo` の打ち間違いとして直したい `kyouhazl` に近い形、`buzzkill`・`quizlet`) を作って base と比べる。

2. **本家 11-18 の誤判定のうち、fork で起きないものを正解表に守る行として足す** — scope: core (正解表とテストだけ。判定ロジックは変えない)
   - 背景: 本家 #2015・#2016・#2017・#2024・#2029 の形 (`itotekinagobyuu`・`ronpa`・`onpa`・`Fluorite`・`uchidome`・`fanntatowirukinnsonn`) は fork では今起きないが、正解表に同じ形の行が無い。PR #24 (019) と同じ考え。
