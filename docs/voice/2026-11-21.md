## 要件定義書の候補
既存の要件 001〜014 (と PR #20 の 016・#23 の 018・#24 の 019・#25 の 020・#26 の 021・#27 の 022)、10-24〜11-20 の文書の候補、`eval/cases/` (`verde`・`ゔぇ` の行は無い) と突き合わせた。11-14 の文書で `metasploit`・`nmapde` の「表示と確定が違う」形を載せたが、そのときは要件にしていない。

1. **`verdeha`・`dokkanoverdeha` で、表示に出ていた `r` が確定で消える問題を直す** (本家 #2161) — scope: core
   - 背景: fork で `dokkanoverdeha` の表示は `どっかのゔぇrでは`、確定は `どっかのゔぇでは`。打った文字が黙って消え、表示と確定が食い違う (11-14 の `metasploit` → 表示 `めたspぉいt`・確定 `めたspぉit` と同じ系統の疑い)。
   - minimum 要件: 日本語の区間に子音だけ (`r`) が挟まったとき、確定で文字を落とさない。少なくとも表示と確定を同じにする。`ver` を英字に残すか (`verでは`) は人が決める。
   - 完成条件の案: 正解表に `verdeha`・`dokkanoverdeha` (と `kanoverde`・`overdeha` を守る行) を足し、直す前は外れ・直した後は当たる。表示と確定が同じことを確かめるテストを足す。Core 全件通過、eval-compare の broken 0。判定ロジックに触るなら査読員が境界例を作って base と比べる。原因が偽の変換エンジン側だけにあるなら、実機 (azooKey) で `r` が消えるかを Mac で確かめるチェックリストを付ける。

2. **本家 11-21 の誤判定の形を、かなのまま (英字にしない) で正解表に守る行として足す** — scope: core (正解表とテストだけ。判定ロジックは変えない)
   - 背景: `atude`・`tasinamu`・`haatu`・`getu`・`subewomotanai` と `Yukishiro` は、本家では英字 (`at`・`mu`・`get`・`be`) が残った形。fork では今どれも起きないが、正解表に同じ形の行が無い。019・020・022 と同じ考え。
   - minimum 要件: 上の形を、今の出力 (`あつで`・`たしなむ`・`はあつ`・`げつ`・`すべをもたない`・`Yukishiro`) で `eval/cases/` に足す。漢字の形は測れないので扱わない。
   - 完成条件の案: 足した行が今の main で当たる。わざと崩した版で外れることを一度確かめる。Core 全件通過、eval-compare の broken 0。

3. **かなの直後の括弧 `()` の幅を決める** (本家 #2150) — scope: core
   - 背景: fork で `kakko()` → `かっこ()` と半角。前回の候補 1 (かなの直後の `*` が全角・`@`・`#` が半角) で幅をそろえるなら、括弧もどちらにするかを同時に決めたほうが手戻りが少ない。
   - minimum 要件: 前回の候補 1 を要件にするときに、括弧 `()`・`[]` を対象に含めるかを人が決める (含めるなら同じ要件、含めないなら今の半角を守る行だけ足す)。Obsidian の `[[…]]` (要件 013) とコードの括弧は今の形を守る。
   - 完成条件の案: 正解表に `kakko()`・`sore(tatoeba)desu` のような形を足し、決めた幅で当たる。要件 013 の行と既存の括弧の行は broken 0。Core 全件通過。
