## 要件定義書の候補
既存の要件 001〜009 (009 は PR #14)、10-24〜11-05 の文書の候補と突き合わせた。`karen`・`beta.`・`rc.`・`-dev.` は過去の文書・`eval/cases/` で `grep` して該当なし。候補 1 は要件 007 (`pre`、PR #12 は閉じたまま) と一部重なる。

1. **版の番号の後ろ (`-pre.3`・`-beta.2`・`-rc.1`・`-dev.3`) が崩れる** — scope: core
   - 背景: 本家 #1603・#1194。fork では `v1.3.1-pre.3` → `v1.3.1-pれ。3`、`-beta.2` → `-べた。2`、`-rc.1` → `-rc。1`。リリースノートや Issue に版を書く人が毎回直すことになる。`-alpha.1` は崩れないので、語によって結果が違う。
   - minimum 要件: 数字と `.` で始まる版の番号 (`v1.3.1`・`1.0.0`) に `-英字.数字` が続く形を、全体で英字のまま残す。`pre` 単独の扱い (要件 007、閉じた PR #12) をどうするかは人が決める。
   - 完成条件の案: 正解表に `v1.3.1-pre.3`・`v1.3.1-beta.2`・`v1.3.1-rc.1`・`1.0.0-dev.3` と守る行 (`v1.3.1`・`v2.0.0-alpha.1`、かなが続く `ver2deshita` のような形) を足し、実装前は外れ・実装後は当たる。Core 全件通過、eval-compare の broken 0。`.` を `。` にする判定に触るので、文末の `desu.` のような日本語の句点への回帰を査読員が境界例を作って base と比べる。

2. **`karento` が `karenと` になる (英単語 + `to` の分け方)** — scope: core
   - 背景: 本家 #1596 (本家 main では `カレント` で直っている)。fork では `karento`・`kyouhakarentode` が `karenと…` になる。`karen` が英単語として見つかり、後ろの `to` が助詞の `と` になる。
   - minimum 要件: `karento` を全部かな (`かれんと`) にする。単独の `karen` (英字のまま) は今の値を変えない。`英単語 + と` (`appleto` など) の今の値は `--repro` で取ってから人が決める。
   - 完成条件の案: 正解表に `karento`・`karentodesu`・`kyouhakarentode` と守る行 (`karen`・英単語 + `to` で英字に残すべき形) を足し、実装前は外れ・実装後は当たる。Core 全件通過、eval-compare の broken 0。境界例 (英単語 + `to`・`te`・`de`) を査読員が作って base と比べる。

3. **ひらがなに直して確定したことも学習する** — scope: core
   - 背景: 本家 #1570 (提案、Windows)。fork も `CompositionController.cs:3839` でかなのまま確定した文節を覚えないので、漢字に誤変換される語を毎回ひらがなに直すことになる。
   - minimum 要件: 変換で漢字が出た文節を、利用者が候補・F6 でひらがなに選び直して確定したときだけ、その読みでひらがなを覚える (初めからかなのまま確定したものは今どおり覚えない)。
   - 完成条件の案: Core のテストに「漢字 → ひらがなに選び直して確定 → 同じ読みを打つとひらがなが先に出る」と「初めからかなで確定したものは覚えない」を足し、実装前は赤・実装後は緑。Core 全件通過、eval-compare の broken 0。学習データのファイル形式を変える必要が出たら止めて人に相談する (CLAUDE.md §5)。
