## 要件定義書の候補
既存の要件 001〜014 (と PR #20 の 016)、10-24〜11-15 の文書の候補、`docs/KNOWN_LIMITS.md` (K34・K75)、`docs/USAGE.md` と突き合わせた。候補 1・2 は Swift・IMK の入力経路と入力ソースの登録 (設定の形) に関わるので、CLAUDE.md §5 により AI だけでは進めず、実機チェックリストを人に渡す形になる。

1. **入力メニューで「英数 (Meltype for Mac)」を選んだら直接入力にする** (Issue #22) — scope: swift
   - 背景: 入力メニューから英数を選ぶと、アイコンだけ英数になって打つと変換される。英数キーなら効く。`applyMode` が ID とだけ比べ、辞書のキー `com.apple.inputmethod.Roman` を英数とみなしていない疑い (コードからの読み)。
   - minimum 要件: 入力メニューで英数を選んだあと `kyouha` を打つと、下線なしで `kyouha` が入る。日本語モードを選び直すと元の変換に戻る。アプリごとにモードを覚える (K75) 動きは変えない。
   - 完成条件の案: TextEdit・Emacs・Safari・ターミナルで「入力メニューで英数 → 打つ」「入力メニューで日本語 → 打つ」「英数キー・かなキー」の 3 通りを記録し、全部期待どおり。直す前に、`setValue` に来る文字列を (同意を得た) トレースか、打った文字を残さないログで確かめる。

2. **日本語モードを ASCII 非対応の入力ソースにできるか調べる** (Issue #21) — scope: swift
   - 背景: 日本語モードが ASCII 対応に見え、Emacs の inline パッチで `C-x b` や dired の 1 文字のコマンドが変換に吸われる。ことえり・azooKey は ASCII 非対応。10-28 の候補 3 と同じ根っこ。
   - minimum 要件: `Info.plist` の `tsInputModeCharacterRepertoireKey` (`Latn` を外す) と辞書のキーのどちらで値が変わるかを実機で確かめ、日本語モードが `ascii=no` になる。英数モードは `ascii=yes` のまま。英語の自動判定・Caps Lock の切り替え・コード系アプリで英数から始まる動き・パスワード欄は変えない。
   - 完成条件の案: 実機で日本語・英数の両モードの `kTISPropertyInputSourceIsASCIICapable` を記録し、Emacs (`emacs -Q` + inline パッチ) で `C-x b`・dired の `n` がコマンドとして効く。入力ソースの登録が変わるので、更新したあとにログアウト・ログインが要るか (K63) と、ほかのソフト (ime-auto.nvim など) の見え方の変化も記録する。ASCII 非対応にしたときの損 (英語を自動で打てる設計との兼ね合い) は人が判断する。

3. **`dainyuu` などの `-inyuu` の形を正解表に守る行として足す** — scope: core (正解表とテストだけ。判定ロジックは変えない)
   - 背景: 本家 #1946 で `dainyuu` → `だinゆう` (英単語 `in` を拾った形)。fork では今起きないが、正解表に同じ形の行が無いので、後の変更で崩れても回帰ゲートで気付けない。
   - minimum 要件: `dainyuu` → `だいにゅう`、`kinyuu` → `きにゅう`、`yunyuu` → `ゆにゅう`、`hensuunidainyuu` → `へんすうにだいにゅう` (比べ方は既存の行に合わせる) を `eval/cases/` に足す。
   - 完成条件の案: 足した行が今の main で当たる (守る行なので最初から緑。わざと崩した版で外れることを一度確かめる)。Core 全件通過、eval-compare の broken 0。
