# Meltype for Mac 戦略計画 (2026-10 版): 本家に負けない仕組みと、Mac でしか出せない価値

作成: 2026-10-13。調査レポート A (本家と利用者)・B (競合 IME)・C (自前コードの棚卸し) を統合した提案で、独立した査読を 3 回通した版です。§8 の 8 件はリョウさんが 2026-10-13 に決定済み (各項目の末尾に「→ 決定」)。数字は 2026-10-13 時点。推測は「(推測)」、確認していないことは「(未確認)」と明記しています。コード上の名前は本文から外し、§9 と括弧内に寄せました。

## 0. 要約 (10 項目)

1. 本家 (Windows 版) は公開 2 週間で Star 988・merged PR 245 件・毎日リリース。外部貢献者が「1 語 1 PR」で誤判定を潰しており、速度とコミュニティでは正面から勝てません。
2. 本家は Mac/Linux を「プレビュー版」と宣言し、Mac に設定画面・辞書画面・更新通知・アプリ種別判定を持っていません。Mac 版フォークはそこを既に持っていますが、Star 2・DL 1 桁で、ほぼ誰にも届いていません。
3. 共通の壁は、判定がルール + 辞書の積み上げで頭打ちなこと (小文字の人名、`pro|to` 型、長文ほど外れる) です。確定し直しは、本家ではアプリのテキストを壊す報告があり (#516 ほか)、Mac 版は逆に安全側に倒してあるので LibreOffice・Google ドキュメントでは直せません。
4. Mac 版だけが今すぐ使える武器は azooKey です。同じライブラリの 1 オプションで Zenzai (ニューラル変換) が使えます。ただし「Zenzai を ON にする」こと自体は本家 Mac 版にも、Mozc フォーク (Mozkey) の前例から Windows にも可能なので、先行価値は「Zenzai × 日英判定の統合」と「計測結果」にあります。
5. 提案する「負けにくい仕組み」は 5 本の柱です: (A) 測って下回らない、(B) 外したときに 1 キーで直せる、(C) 変換精度で先行する、(D) Mac ユーザーに届く経路、(E) 本家の速度に追従する仕組み。
6. 柱 A が全ての前提です。正解表 (ゴールド表) が今は一時の作業用フォルダーに散逸しているため、まずリポジトリに入れ、本家のテストコーパスも同じ表で回せる形にします (手元のコミットまでは公開行為なし。push すれば正解表の中身も公開になるので §8 の 8 で判断。低リスク、2〜3 週)。
7. 斬新な案: (1) Zenzai の言語モデルを「迷ったときの最終判定」に使う (仮説、実験で go/no-go)、(2) 判定の理由が見える辞書アプリ、(3) ターミナル内チャット (Claude Code・Hermes) 特化、(4) Apple Intelligence のローカル LLM で「英語部分だけ整える」。
8. やらないこと: Windows 版との機能競争、署名基盤・CI、クラウド変換、独自機能の本家への PR (理由は §6)。
9. 最大のリスクは本家が Mac に本気を出すことです (外部貢献者が設定画面の設計案 #523 を出している。英数状態のローマ字検知は本家 Windows に最初からあり、本家が Mac に移植すれば差が 1 つ消える)。だから本家が真似しにくい柱 A・B と §5.1 を先に固めます。
10. 判断事項 8 件 (§8) は決定済み: 本家への PR と issue への知らせは現時点では行わず (5b・6c)、それ以外はおすすめどおり。公開行為 (README への比較表と正解表の push、Homebrew の tap 新設、本家への連絡) は全て §8 で許可を取る形にしています。

## 2. 「勝つ」の定義 (提案)

Star 数で本家全体を超えるのは、利用者の大半が Windows である以上、現実的ではありません。おすすめする定義は次の 3 つの数字です。

| 指標 | 今 | 目標 (半年) | なぜこれか |
| --- | --- | --- | --- |
| 判定精度 (同じ正解表で本家 Core と比較) | 未計測 | 本家の数字を下回らない + Mac 固有コーパスで上乗せ | 「負けにくい」を数字で示せる唯一の軸 (条件は柱 A) |
| Mac での到達 (1 版あたりの DL) | 1 桁 | 本家 Mac zip の直近版 (約 200) を超える | Mac ユーザーが「Mac はこっち」と選んでいる証拠 |
| 変換・操作の満足 (Issue の「使えない」系の比率) | 計測なし | Issue で「乗り換えた」報告が出る | 機能数ではなく体験の指標 |

## 3. 負けにくい仕組み: 5 本の柱

### 柱 A. 測って下回らない (評価基盤) — 全ての前提
- 何を (2 段):
  1. リポジトリ内で測れるようにする (手元のコミットまでは公開行為なし。公開リポジトリへ push した時点で正解表の中身も公開になるので、push 前に私的な文を除く選別と §8 の 8 の判断が要る): 日英混在コーパス + 正解表を `eval/` に置き、スクリプト 1 本で「本家 main の Core」と「Mac 版 Core」の数字を並べる。本家の `--eval` / `--mixed-bench` のコーパス (GPL なので取り込める) も同じ表で回す。リョウさんの実機結果 (「打った>結果」形式) を毎回そのまま足す運用にする。
  2. 結果を README に載せる (公開行為。§8 の 8 で判断)。
- なぜ負けにくいか: 本家の判定修正を取り込み、本家のテストコーパスも同じ表で回す限り、本家の数字を下回りません。上乗せ分は Mac 固有のコーパス (ターミナル・AI ツール名・US 配列) で示します。
- 条件 (ここが崩れると成り立たない): 本家の修正を選別して取り込んでいる (P40〜P44 が保留・未着手) ので「全部取り込んだ」とは言えない。比較は擬似エンジン上の Core の数字で、実機 (macOS スペルチェッカー・azooKey) の体感とは別。本家も PR ごとに同じ比較を CI で回しているので、同じ数字を公開するのは本家にも簡単。
- 得と損: 得 = 回帰ゼロの保証、取り込みの判断が速くなる、公開すれば信頼。損 = 正解表の整備に人手 (1,000〜2,000 行を目標)、リポジトリに数 MB のテキストが入る。

### 柱 B. 外したときに 1 キーで直せる (修正 UX)
- 何を: 確定した直後の語を「日本語 ⇔ 英語」でトグルするキー (例: Ctrl+T、または「英数」「かな」の 2 回押し)。既存の再変換 (Shift+Space) と統合し、直した結果は前後の語を含めて学習する。効かないホストでは「何も起きない」を保証する。
- 本家・Mac 版に既にあるものとの差: 変換中の語を F6/F10 で直して学習する仕組みは両方にあります。無いのは「確定した後」の 1 キー修正と、前後の語を含めた学習 (本家 #491 の先行) です。競合調査でも、失敗時の修正コストを設計の中心に置いた IME は見つかりませんでした (部分的な前例: iIME の Backspace リセット、azooKey の 2 回押し)。
- 得と損: 得 = 利用者の不満「リカバリが面倒そう」「長文ほど外れる」に直接効く。損 = 確定し直しはホストごとに挙動が違う (LibreOffice・Google ドキュメントでは効かない (C §5)。Hermes チャット欄などの Electron 系は原因未調査) ので、効かないホストの保証を先に作る必要がある。難しさ: 中。

### 柱 C. 変換精度で先行する (Zenzai・個人学習)
- 何を: azooKey の変換オプションで Zenzai を有効化 (設定で ON/OFF、既定は計測後に決定)。推論上限 1〜5 回でライブ変換の予算内に収める。azooKey 側の個人 n-gram (α ブレンド) と履歴リセット UI も載せる。モデルは azooKey-Desktop と同じ zenz-v3.1-small (73.9 MB) か zenz-v3-small (72.3 MB) のどちらかを 1-1 の実験で決める。
- 根拠: Zenzai は Anthy コーパス 1,745 文で従来型 1,065 → 1,179 正解 (著者の公開ベンチで約 1 割の文が改善)、難問 150 問で 56 → 100。1 操作 40 ms 程度 (M2 Pro)。文書上はメモリ約 150 MB・GPU 使用・M1 以上が望ましい (未実測)。
- なぜ先行できるか (限定付き): 本家 Windows の今の構成 (MS-IME + Mozc) には Zenzai がありませんが、Mozc フォーク Mozkey が Zenz 補正を載せた前例があり (B §2)、本家 Mac 版も azooKey なので、本家が追随できないわけではありません (Windows は CUDA 前提と Zenzai の文書にある)。Mac 版の先行価値は「ON にする」ことではなく、§5.1 の「Zenzai × 日英判定」の統合と、計測結果にあります。
- 得と損: 得 = 「切替不要」の価値が日本語側の誤変換で半減する問題を解く。損 = 配布物が約 21 MB → 約 95〜100 MB (推定: 重み 72 MB は圧縮が効かない + `llama.framework` 5.6 MB)。遅延・メモリは未実測、差分変換 (P21) との相性も推測段階、Intel Mac 未確認。対策候補: 重みを同梱せず、設定で ON にしたときだけ Hugging Face から取得 (通信が 1 種類増えるので、プライバシーの文言を更新)。難しさ: 中。

### 柱 D. Mac ユーザーに届く経路
- 何を: (1) 自前 tap の Homebrew cask (tap の新設は公開リポジトリを増やす公開行為。§8 の 2 で許可済み)。(2) 本家 issue #229 (Homebrew)・#508 (設定画面) に「Mac 版フォークで実装済み」と知らせる、または作者に直接連絡して本家 README から誘導してもらう (**現時点では行わない**: §8 の 6 の決定。再検討はリョウさんの指示があったとき)。(3) Mac 系メディア・Zenn への記事 (Mac 固有の訴求: 「英数/かな の押し忘れが直る」「英語混じりの文で切替が要らない」「US 配列で快適」「ライブ変換との違い」(Mac 標準の日本語入力の動きを実機で確かめてから書く。それまでは Meltype の動きだけを書く))。[訂正 2026-10-15: 「ライブ変換との違い」に、Mac 標準の日本語入力の動きを確かめてから書く条件を足した。README FAQ・K51 と同じ方針] (4) アイコン (本家 #222 の不満。辞書アプリは汎用アイコンのまま)。
- Homebrew の前提 (推測・実機未確認): cask には入力ソース用の置き場がある。署名は Homebrew 側では不要だが、cask で入れたファイルには quarantine 属性が付くので、ad-hoc 署名の IME がそのまま起動するかは要確認。起動しない場合は `--no-quarantine` の案内か、cask の後処理で外す (今の `install.sh` 相当を cask に移す)。
- なぜ: 本家 README・窓の杜の記事はすべて本家 Releases に誘導しており、フォークを知る経路が存在しません。機能で勝っても数字は動きません。
- 柱 A との整合: 「本家より上」と README に出しながら作者に誘導を頼むのは両立しにくいので、比較表は「本家の修正を取り込んだ上で Mac 固有分を足した結果」という協調的な書き方にします (§8 の 8)。
- 得と損: 得 = 到達 1 桁 → 本家 Mac 並みの可能性。損 = (1)(2)(3) は公開行為でリョウさんの判断が必須。本家に知らせると、本家が Mac 版の機能を自前で実装する動機にもなる (両刃)。Homebrew は版ごとに cask の SHA 更新が増える (スクリプト化可能)。難しさ: 低〜中。

### 柱 E. 本家の速度に追従する仕組み
- 何を: 本家の新コミット・PR を毎日取得し、「Mac 版に関係あるか / 取り込み済みか / 衝突するか」を分類して取り込み管理表の候補行にする半自動スクリプト (エージェントの定期実行)。取り込みの判断と査読は今までどおり人 + 独立査読。
- なぜ: 本家は PR 全体で 1 日 15 件前後、うち判定・変換の修正が多数です。手動追従では半年で確実に遅れ、追従が切れた瞬間に柱 A の「下回らない」が崩れます。
- 得と損: 得 = 追従コストの固定化。損 = 定期実行の運用と、取り込み判断の負荷は残る。難しさ: 低〜中。

## 5. 斬新な案 (詳細)

### 5.1 Zenzai で「迷ったときの最終判定」(仮説)
- 今の判定は文字列のルールで、「`pro|to` は文字列だけでは区別不能」と結論済みです。
- 方式案: 判定が「分からない / 保留」のときだけ、候補の分割 (全部日本語 / 一部英語) を比べる。常時ではなく確定時 (Enter/Space) と確定し直しのときだけ走らせ、1 回 40 ms 程度の予算に収める。
- 注意 (査読の指摘): zenz モデルは「かな → 漢字」の課題形式で学習された文字レベル日本語 GPT-2 で、汎用の「文の自然さ」採点器ではありません。英字を含む区間の尤度は学習外です。そこで、まず「全部日本語として変換したときの尤度の低さ」だけを手がかりにする案から試します。採点には azooKey の変換 API ではなく llama.cpp を直接呼ぶ必要があります (推測)。
- 置き場所: ルールを置き換えるのではなく、判定の入口 (スコア計算と区間判定の 2 か所) に「ルールが迷ったときの最終判定」として足すので、既存テストが守れます。
- go/no-go の基準: 正解表の「迷ったケース」N 件で改善が一定数以上、かつ確定時の追加遅延 40 ms 以内。出なければ捨てる (実験 1〜2 週)。

### 5.2 判定の理由が見える
- 判定の内訳 (「英語辞書に一致 +5」「拗音 +3」など) は Core に既にあります。辞書アプリに「判定を調べる」タブを足し、ローマ字を入れると内訳と、ユーザー辞書・学習した語への登録ボタンを出します。
- 本家にも他 IME にも無い透明性で、「なぜこうなった」の問い合わせが自己解決に変わります。

### 5.3 ターミナル内チャット特化
- Claude Code・Hermes・Codex のようにターミナルで日本語の会話をする用途が増えています。今のアプリ別設定はアプリ単位の ON/OFF だけです。「Terminal でもチャット行は日本語」を切り替える軽い手段 (入力メニューの一時切替、または行頭のプロンプト文字の検出 (推測: 取れるかはホスト次第)) と、Shift+Enter・コマンド行の英数維持・保護区間 (URL・パス) を組み合わせます。

### 5.4 英語部分だけ整える (Apple Intelligence のローカル LLM)
- azooKey-Desktop v0.1.3 が macOS 26 の Foundation Models で「いい感じ変換」を既定で使えるようにしています。Meltype は英語混在文なので「英語部分の綴り・文法だけ直す」「選択して英訳/和訳」が自然な使い方です。全てローカルで、プライバシー方針を変えずに済みます。条件は macOS 26 + Apple Intelligence が ON の対応機種。

### 5.5 「英数」「かな」キーに第 2 の意味を載せる
- Meltype では切替キーの役目が軽くなるので、「英数 2 回押し = 直前語を英語に」「かな 2 回押し = 日本語に」のように柱 B の修正キーとして再利用できます (azooKey の「2 回押しで翻訳」と同じ発想)。US 配列でも押せる割り当てを別に用意します。

## 6. やらないこと (理由つき)
- Windows 版との機能競争: Windows は対象外 (方針)。Core の変更が Windows に波及する点は「対象外」と記録し続ける。
- 署名基盤・CI・Developer ID: 運用コストの方針どおり。Homebrew は署名なしでも成立する見込み (quarantine の扱いは要確認)。
- 学習・辞書のクラウド同期 (iCloud Drive を含む。3-1 を 2026-10-15 に取りやめ): ローカルだけで処理することが Meltype の価値。複数の Mac で揃えたい人は、ユーザー辞書を辞書アプリの書き出し (⇧⌘E)・取り込み (⇧⌘I) で手で移す (学習データを移す手段があるかは未確認)。
- クラウド変換・クラウド学習: 「打った内容をネットワークに送らない」が Mac 版の売りの一つ。Zenzai の重み取得は「設定で ON にしたときだけ」の通信に限定し、P43 の誤判定の報告は利用者が押したときだけ (自動送信なし) にして、方針文を更新する。
- 本家への PR (独自機能も Core のバグ修正も、現時点では出さない: §8 の 5 の決定): Mac 版は GPL なので、PR を出さなくても本家が公開コードを取り込むこと自体は止められません。ただし CLA 無しのコードを取り込むと作者の再許諾権を損なうため取り込まれにくく、PR を出すとその障壁が無くなります。
- かな入力派・明示切替派の取り込みを主戦場にしない: 本家も弱く、Mac 版は既に最低限対応済み。訴求の中心は「ローマ字で英語混じりを打つ Mac ユーザー」。
- ルールの判定を機械学習に全面的に置き換える: 判定の土台 (区切りの単位・単語判定の yes/no の契約) から作り直す大改修になる。§5.1 の「迷ったときだけ」で代替する。
